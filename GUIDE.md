# Работа с гостевыми VM

## Первый запуск

Запускайте команды на Linux-хосте из корня репозитория. На хосте нужны GNU Make, Docker Engine с Compose v2 и разрешённый Docker доступ к устройству `/dev/kvm`. Рабочий стол и браузер на сервере не требуются.

```sh
make
```

Это то же самое, что `make vm-setup VM=vm-01`. Команда создаёт `.env` из шаблона, если его ещё нет. Она проверяет доступность KVM, запрашивает upstream, проверяет доступ через него и готовит гостя. Во время ввода адрес прокси не отображается в терминале.

Если на хосте уже есть образ Node.js с тегом `22-bookworm-slim`, Make использует его для предварительной проверки прокси. При отсутствии образа нужен настроенный HTTPS-прокси Docker daemon или заранее загруженный базовый образ. Для первичной проверки прокси до загрузки базового образа используется `curl` хоста. APT проверяет TLS через встроенные публичные корневые сертификаты Mozilla из Node.js. Корпоративные CA хоста автоматически не импортируются.

Начальный набор параметров в `.env`:

```dotenv
VM_COUNT=1
VM_VCPU=2
VM_RAM_MB=4096
VM_DISK_GB=12
VM_NETWORK_PREFIX=10.215
```

`VM_COUNT` задаёт диапазон при пакетном запуске через `make vm-up`. Обычный `make` подготавливает только `vm-01`. Сеть каждого гостя создаётся отдельно. Измените `VM_NETWORK_PREFIX` до подготовки, если подсеть пересекается с сетью хоста.

## Создание гостя и смена прокси

```sh
make vm-setup VM=vm-02 VCPU=2 RAM_MB=4096 DISK_GB=12
make vm-proxy VM=vm-02
```

Ресурсы сохраняются при создании. Запуск `vm-setup` на уже подготовленном госте сохраняет его диск. Для гостя с сохранёнными ресурсами используйте эти же значения. `vm-proxy` проверяет новый адрес перед заменой действующего.

Состояние настройки хранится в `.v2-state/vm-XX`. В файле `upstream` хранится HTTP-адрес прокси, при необходимости с логином и паролем в URL. Для ручной настройки создайте файл с правами `0600`. Этот файл подключается только к соответствующему шлюзу. Не добавляйте его в Git.

Файл `allowed-domains` в том же каталоге задаёт разрешённые полные доменные имена по одному на строку. При загрузке гостя тестовая схема сопоставляет их с адресом его шлюза. Шлюз проверяет имя назначения по SNI для HTTPS и по Host для HTTP. TLS-соединение с целевым сервисом проверяет само приложение. Для применения правок в списке остановите гостя и запустите его снова. IPv6 из гостя отключён, публичные порты Compose не публикует. Перед запуском QEMU контейнер включает nftables в своём сетевом пространстве. Исходящие IP-соединения разрешены только к шлюзу этой VM на TCP 80 и 443. Если правило установить не удаётся, VM не запускается. После установки правила QEMU запускается без Linux capabilities.

Чтобы проверить внешний IP прокси из ВМ, выполните:

```sh
curl -fsS --max-time 15 https://icanhazip.com/
```

## Терминал atrice

`atrice` — терминальное приложение для тех же операций: список окружений, создание, запуск, консоль агента, Git-шлюз, журналы и удаление. Всю работу с Docker, QEMU и шлюзом по-прежнему выполняет `v2/manage.sh`, поэтому поведение команд и проверок совпадает с `make`.

Соберите бинарник из корня проекта. Нужен Go 1.21 или новее, внешние зависимости не используются:

```sh
make atrice
./atrice
```

Чтобы вызывать `atrice` из любого каталога, установите его в каталог
пользователя — root не нужен:

```sh
make atrice-install          # положит бинарник в ~/.local/bin
bash cli/install.sh --bind   # и привяжет этот каталог проекта
```

Установленный бинарник лежит вне проекта, поэтому корень `agent-docker` он
ищет так: явный `--root`, затем `AGENT_DOCKER_ROOT`, затем поиск вверх от
каталога бинарника и от текущего каталога, и только в конце — привязка из
`~/.config/agent-docker/root`. Привязка последняя намеренно: находясь внутри
какого-то клона `agent-docker`, вы работаете именно с ним. Файл привязки
пишется только по `--bind`, без него уже настроенный каталог не меняется.

Имя бинарника ни на что не влияет: приложение не смотрит на то, как его
вызвали, поэтому собранный раньше `agd` работает по-прежнему, а поставить
его под прежним именем можно через `bash cli/install.sh --name agd`.

Каталог установки задаётся `--prefix DIR`. Относительный путь считается от
каталога, из которого вызван установщик, а не от корня проекта:
`bash cli/install.sh --prefix bin` из домашнего каталога положит бинарник
в `~/bin`. Установщик печатает полный путь — файл лежит именно там.

Запуск без аргументов показывает список гостей с выбором стрелками вверх и вниз или `j` и `k`. Стрелки понимаются в обоих видах — обычном (CSI) и в режиме приложения (SS3), который включают tmux и screen, — а `Enter` принимается и как CR, и как LF.

`Enter` — это подтверждение подсвеченного пункта, и только оно. В списке гостей он выбирает гостя и открывает экран его живых сессий; в списке сессий — возвращает в подсвеченную сессию: отсоединённую открывает `vm-session-open` (имя сессии уходит в `RESUME`), а к уже подключённой — а именно так выглядит сессия после `Ctrl+]` или закрытия терминала — возвращает обычной консолью, потому что её клиент `tmux` работает в консоли гостя и оболочку не отпускает. Экран говорит об этом строкой под таблицей. Подключение к сессии ничего не поднимает: у остановленного гостя живых сессий нет, и ради `attach` он не запускается. Сам по себе `Enter` ничего не запускает: ни гостя, ни Claude, и оболочку не открывает. Если живых сессий нет, подтверждать нечего, и экран говорит об этом строкой состояния. Обычная консоль осталась отдельным пунктом — `c`. Клавиша `a` на экране сессий создаёт **новую** управляемую сессию `tmux` рядом с уже работающими: имя `claude-<16 шестнадцатеричных знаков>` выдаётся на хосте, сессия открывается сразу, а прежние сессии и их процессы продолжают работать — к ним ничего не отправляется. После `Ctrl+]` в живом списке видны обе, и `Enter` открывает ровно подсвеченную. Если консоль гостя занята — в ней работает клиент сессии, — создание отказывает строкой состояния и ничего не запускает: команда ушла бы этому клиенту как нажатия клавиш. Сначала отсоединитесь от сессии внутри `tmux` или выйдите из агента. Отказ не оставляет ни сессии в госте, ни записи о входе, поэтому повторное нажатие ничего не дублирует. На остановленной ВМ новой сессии нет: её запускает обычный `a` из списка гостей (цель `claude`), которая поднимает гостя. На экране сессий `r` обновляет данные, а `Ctrl+]`, `Esc` или `q` возвращают в список.

Отсоединение от консоли или сессии по `Ctrl+]` сразу возвращает в список, и выбранный гость остаётся под курсором — можно тут же перейти к следующему. Остальные действия вызываются клавишами: `c` — консоль, `a` — Claude, `u` — запустить, `s` — остановить, `n` — создать, `g` — показать или изменить настройку Git, `l` — журналы, `p` — профиль, `d` — удалить, `r` — обновить список, `q` — выход. Удаление из списка всегда сохраняет диск. Тот же экран открывает `atrice menu`. Меню работает на отдельном полноэкранном экране терминала. Его кадры не попадают в историю прокрутки, а при выходе возвращается прежний экран.

Клавиша `n` создаёт ВМ. Если пропустить технический ID, Atrice выберет
свободный номер. Для списка можно задать своё имя при создании или изменить
его клавишей `m`. Клавиша `e` продолжает подготовку незавершённой ВМ или
меняет прокси настроенной. Вставляйте прокси как `user:password@host:port`
или как полный HTTP URL. Терминал скрывает ввод. Клавиша `d` убирает ВМ
из списка и сохраняет диск с настройками. Вернуть её можно командой
`atrice setup <VM>`.

Клавиша `i` открывает авторизацию Claude Code внутри выбранного гостя.
Откройте ссылку из консоли на хосте и войдите в нужный аккаунт. Для прогона
без прежнего контекста используйте отдельного гостя и запустите новую сессию
клавишей `a` на экране живых сессий.

Если хостовый терминал закрыли, не нажав `Ctrl+]`, консоль гостя больше не остаётся висеть с захваченной блокировкой `/guest/console.lock`: закрытое устройство терминала консоль замечает сама, а про ушедшего клиента `docker exec` ей сообщает хост — `v2/manage.sh` по ловушке на `HUP`, `TERM` и выходе просит гостя освободить консоль с токеном именно этого входа. Повторный вход после этого работает сразу. Чужую работающую консоль освобождение не трогает (токен не совпадёт), а гостю при этом не отправляется ни один байт, поэтому запущенный агент и сессии `tmux` переживают закрытие клиента. Отказ при действительно занятой консоли теперь называет процесс, который её держит.

Подключение к выбранной сессии и запуск агента отправляют команду в оболочку гостя, поэтому они ждут признака, что Bash вернулся к приглашению: гостевой профиль `/etc/profile.d/agent-docker-serial.sh` печатает невидимую отметку при каждом возврате к приглашению. По виду строк в журнале готовность не угадывается — «`progress # `» печатает и работающая программа, и отправленный в неё `attach` ушёл бы ей как нажатия клавиш. Гость, созданный прежней версией, эту отметку печатает только один раз за вход: профиль попадает внутрь при создании гостя. Чтобы обновить его без пересоздания, откройте консоль (`make vm-console VM=vm-02`) и выполните в ней

```
sudo tee /etc/profile.d/agent-docker-serial.sh > /dev/null <<'EOF'
<содержимое v2/serial-profile.sh>
EOF
```

затем выйдите из оболочки (`exit`) и войдите заново — новая оболочка читает профиль при входе. До обновления на таком госте подключение к сессии и запуск агента проходят только из свежей оболочки, сразу после входа в Bash; обычная консоль по `c` работает всегда.

Агент по `a` из списка гостей запускается внутри управляемой сессии `tmux` на общем сокете, поэтому он виден в колонке «СЕССИИ», переживает закрытие окна и доступен повторным входом. В образе без `tmux` запуск остаётся прямым, как раньше. Обычный `tmux`, запущенный в госте вручную без общего сокета, в список не попадает: это сессия пользователя, а не Atrice.

Если в serial-оболочке работает приложение, запущенное прямо в ней — так выглядит гость старого образа или агент, запущенный до этого обновления, — список говорит «на serial работает приложение», а запуск агента и новая сессия отказывают до отправки: команда ушла бы этому приложению как нажатия клавиш. Безопасный путь один и ничего не завершает за вас: войдите обычной консолью по `c`, выйдите из приложения штатно (например `/exit` в Claude), и оболочка вернёт приглашение — после этого работают и `Enter`, и `a`. Перезапускать гостя для этого не нужно, и ваши процессы Atrice не завершает.

При обычном входе консоль показывает хвост журнала без управляющих режимов прежнего приложения: иначе вход включал бы в вашем терминале отслеживание мыши и альтернативный экран, из-за чего экран выглядел повреждённым, а выделение текста требовало Shift. При выходе по `Ctrl+]` эти режимы сбрасываются в вашем терминале. Пока приложение работает, оно распоряжается мышью само — это его режимы, и консоль их не трогает. Размер окна serial-линия не передаёт: новые размеры уходят гостю только когда оболочка ждёт приглашение, а приложению, запущенному до изменения размера, их придётся обновить после выхода в оболочку.

Мышь. Пока приложение в госте включило отслеживание мыши, щелчки и перемещения достаются ему, и обычное выделение текста в терминале остаётся только с Shift — это захват мыши приложением, а не залипание: после выхода консоль режимы сбрасывает. Если выделять нужно мышью без Shift, запустите `MOUSE=off atrice` и откройте консоль или прямую сессию из меню. Для запуска консоли без меню используйте `MOUSE=off make vm-console VM=vm-02`. Тогда включения отслеживания снимаются из потока, терминал остаётся в обычном режиме, а приложение щелчков мыши не получает — клавиатура работает как всегда. В гостя при этом ничего не отправляется.

Размер окна. Если окно меняли, пока в оболочке работало приложение, размер не теряется: он уйдёт гостю сам, как только оболочка вернёт приглашение. Внутри активной сессии `tmux` размер не передаётся — команда ушла бы клиенту как нажатия клавиш; после выхода в оболочку он применится.

### Параллельные сессии при занятом serial

Обычный путь в гостя один — его serial-консоль, и пока в ней работает приложение или клиент живой сессии, отправить туда ничего нельзя: байты ушли бы этому процессу как нажатия клавиш. Поэтому создать сессию рядом этим путём невозможно, и `a` в таком состоянии честно отказывает.

Для этого есть **прямой вход** — отдельный путь, который serial не затрагивает: свой порт virtio-serial, своя гостевая служба и свой клиент `tmux`. При нём `a` создаёт и сразу открывает новую сессию даже при занятой оболочке, `Enter` открывает ровно подсвеченную сессию по имени, прежние сессии и их агенты продолжают работать, а повторный вход с тем же именем подключается к той же сессии, а не создаёт вторую. Размер окна на этом пути доходит и до активной сессии.

Включается он явным шагом и только там, где это нужно; на рабочих ВМ по умолчанию его нет, и всё работает как раньше. Порядок на стенде:

1. Порт появляется при следующем запуске гостя (`v2/guest.sh` добавляет его в аргументы QEMU), поэтому остановите и запустите гостя стенда: `make vm-stop VM=vm-09 && make vm-up VM=vm-09`.
2. Поставьте службу тем же узким установщиком, что и канал списка, с явным флагом: на остановленном госте со смонтированным корнем — `bash v2/install-sessions-guest.sh --install --root /mnt/vm-09 --with-direct`, внутри работающего гостя от root — `bash install-sessions-guest.sh --install --with-direct`. Без флага прямой вход не ставится и не включается. Если прежняя служба уже активна, обновление применяется при следующем запуске гостя. Так работающие сессии остаются открыты до согласованной остановки.
3. Проверка: `bash v2/install-sessions-guest.sh --check --root /mnt/vm-09 --with-direct` перечисляет все файлы и включённые юниты, а с хоста `make vm-session-direct-check VM=vm-09` отвечает `ready`. Без службы или сервера tmux ответ `silent`, без порта — `absent`; в обоих случаях TUI работает по-прежнему через консоль.

Сервер tmux запускается отдельной службой под пользователем `agent`. Claude получает обычный доступ гостя к сети и домашнему каталогу. Служба прямого входа принимает два сообщения — проверку связи и открытие сессии с именем вида `claude-<16 шестнадцатеричных знаков>`; команду клиента не берёт из запроса (она фиксирована), оболочку не запускает, сети не имеет, портов не публикует и туннелей не открывает. Выход — `Ctrl+]`: клиент отсоединяется, сессия и агент остаются живы. Если окно закрыли без `Ctrl+]`, вход освобождается сам: хост по ловушке просит завершить ровно то реле, которое этот вход и запустил, а оно перед уходом отсоединяет клиента сессии. Поэтому следующий вход доступен сразу и ничего завершать руками не нужно. Если и хостовая половина пропала целиком, остаётся запас: служба замечает пропажу подтверждений и отсоединяет клиента через несколько секунд. Вход с другого окна в это же время тоже работает: он отпускает прежнего клиента и подключается сам, не трогая сессию и агента.

Клавиши работают в обеих раскладках: нажимается та же клавиша, русская буква сворачивается по расположению. То есть `с` — консоль, `ф` — Claude, `г` — запустить, `ы` — остановить, `п` — git, `д` — логи, `з` — профиль, `в` — удалить, `т` — создать, `к` — обновить, `й` — выход, `о` и `л` — вниз и вверх. Заглавные буквы и Caps Lock тоже работают.

Колонка «СЕССИИ» показывает только живые сессии и только по данным канала: `atrice` опрашивает цель `vm-sessions-check` у запущенных гостей не чаще раза в пять секунд, а `r` спрашивает заново. Состояния не смешиваются: `1 сессия: claude` — список получен (звёздочка означает, что к сессии кто-то подключён), `сессий нет` — канал работает и сессий нет, `старый образ` — образ гостя канала не умеет, `нет tmux` — в образе нет tmux, а `служба не ответила`, `нет доступа к tmux`, `формат не разобран`, `канал не успел`, `ответ испорчен` и `опрос не удался` — разные неисправности канала, а не отсутствие сессий. Отметка `консоль занята` добавляется отдельно. Незнакомое состояние показывается как есть: поле расширяемо. У остановленного гостя канал не спрашивается вовсе. Память CLI о том, какой агент и проект открывали последними, осталась в `atrice status` строкой «Последний вход из CLI».

Если список живых сессий ведёт себя непонятно, диагностика скажет, что именно не так:
`make vm-sessions-check VM=vm-02` печатает одну строку JSON и не падает ни на одном состоянии.
Состояния различаются: `old-image` — образ гостя без канала сессий, `no-service` — канал есть, но
гостевая служба не ответила, `no-tmux` — в образе нет tmux, `no-permission` — служба не видит
сокет tmux (живые сессии при этом могут быть), `empty` — сессий нет, `live` — список получен.
Отдельным полем `console` показано, занята ли сейчас пользовательская консоль гостя. Диагностика
ничего не запускает и в консоль гостя не пишет, поэтому её можно вызывать при работающем агенте.

Клавиша `c` открывает обычную serial-консоль гостя и работает на любом образе: ни tmux, ни запущенный агент, ни канал сессий для неё не нужны. Если гость не настроен или остановлен, список скажет об этом строкой состояния и команду запускать не станет. Отказ самой команды — например «Консоль этого гостя уже открыта» — остаётся на экране до `Enter`, а удачный выход по `Ctrl+]` возвращает в список сразу.

`/go vm-01` в строке команд и `atrice go vm-01` возвращают в гостя, и цель выбирает канал: если он отвечает живыми сессиями, открывается консоль и показывается хвост журнала за время отсутствия; если канал отвечает пустым списком, запускается Claude. Когда канала нет — старый образ или отказ опроса, — решает память CLI о прошлом входе: другого источника там не появится. Остановленный гость поднимается запуском Claude. Если канал сообщает, что консоль гостя занята, возврат отказывает сразу и просит выйти из неё по `Ctrl+]`: иначе отказ пришёл бы изнутри гостя. Возврат через консоль не меняет запомненные агент и проект.

Строка команд со слешем осталась отдельным режимом и вызывается как `atrice cmd`. Команды в ней начинаются со слеша и совпадают с подкомандами: `/go vm-01`, `/logs vm-02 --tail 20`, `/rm vm-03`. `Tab` дополняет команду и имя гостя, стрелки вверх и вниз листают историю, а одно имя гостя без слеша открывает его сессию. Выход — `/quit` или `Ctrl+D`.

| Команда | Действие |
| --- | --- |
| `atrice ls` | Список гостей: состояние, ресурсы, прокси, назначение Git и живые сессии по данным канала. |
| `atrice go vm-02` | Вернуться в гостя: к живым сессиям из канала через консоль, в свободного — запуском Claude. |
| `atrice status vm-02` | Подробное состояние одного гостя, включая строки контейнеров. |
| `atrice new vm-03 --cpu 4 --ram 8192 --disk 40` | Создать и подготовить гостя. |
| `atrice setup vm-02` | Повторная подготовка после обновления образа. |
| `atrice up [vm-02]` | Запустить гостя, без имени — всех настроенных. |
| `atrice stop vm-02` | Штатно выключить гостя и остановить шлюз. |
| `atrice console vm-02` | Открыть консоль гостя. |
| `atrice claude vm-02 --project my-project --resume "Название сессии"` | Открыть Claude в проекте и продолжить сессию. |
| `atrice auth vm-02`, `atrice logout vm-02` | Вход и выход Claude Code внутри гостя. |
| `atrice proxy vm-02` | Задать upstream-прокси гостя. |
| `atrice git vm-02 --repo owner/name --write test/branch` | Назначить репозиторий GitHub. |
| `atrice git vm-02 --provider gitlab --url https://gitlab.example.com --repo group/project` | Назначить проект GitLab. |
| `atrice git status vm-02` | Показать назначение шлюза без токена. |
| `atrice logs vm-02 --service proxy --tail 100 --follow` | Журналы контейнеров гостя. |
| `atrice profile vm-02` | Профиль запущенного гостя с идентификаторами оборудования. |
| `atrice sessions vm-02` | Живые сессии tmux гостя. На образе без канала сессий команда скажет, что образ несовместим, и ничего не сломает. |
| `make vm-sessions-check VM=vm-02` | Диагностика подключения одной строкой JSON: что именно сейчас не так. |
| `atrice rm vm-02` | Удалить гостя, сохранив диск. С `--delete-disk` удаляется и диск. |

Живые сессии агентов идут на одном общем сокете tmux — `/run/atrice/sessions/atrice`. Каталог сокета создаётся при загрузке гостя, до запуска службы и агентов, и его путь лежит в переменной `ATRICE_TMUX_SOCKET`: сессия запускается как `tmux -S "$ATRICE_TMUX_SOCKET"`. Поэтому список сессий отвечает одинаково и до первого запуска tmux, и после: пока сокета нет, список пуст, а отказ в доступе к сокету показывается отказом, а не пустым списком.

Гости, созданные до появления канала сессий, получают его отдельным шагом — его выполняет оператор, а не агент. Предпочтительно на остановленном госте, смонтировав его корень на хосте: `bash v2/install-sessions-guest.sh --install --root /mnt/guest`; служба поднимется при следующем запуске. Внутри работающего гостя то же делает `--install` от root. Шаг идемпотентный: при совпадающем содержимом он не пишет ничего, а ключи хоста, учётные данные и профиль VM не затрагивает. Новым гостям он не нужен — им канал ставится при первом запуске.

### Старый гость: установка tmux и канала сессий

Гость, созданный до появления канала, живых сессий не показывает: `make vm-sessions-check VM=vm-02`
отвечает `state: old-image`. Обычная консоль по `c` при этом работает, и работать будет на любом
шаге ниже — она не зависит ни от канала, ни от tmux.

Все шаги выполняет **уполномоченный оператор** — человек с доступом к Docker-хосту. Агент их не
выполняет: он может только подготовить текст и потом проверить результат читающими командами
(`make vm-sessions-check`, `--check`). Процедура ничего не перепровижинирует: `instance-id`
остаётся прежним, ключи хоста SSH, учётные данные Claude, `profile.json`, `/etc/hosts`, диск и
домашние каталоги не читаются и не перезаписываются. Новых прав агенту не выдаётся: установка
идёт из того же списка источников `/etc/apt/agent-docker.list`, что и при первой подготовке.

**1. Снять исходное состояние.** На хосте, гость ещё работает:

```sh
make vm-sessions-check VM=vm-02 | tee /tmp/vm-02.channel.before   # ожидается state: old-image
make vm-profile VM=vm-02 > /tmp/vm-02.profile.before
```

В консоли гостя (`make vm-console VM=vm-02`) записать отпечаток ключа хоста — он понадобится как
доказательство, что ключ не сменился:

```sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
cat /var/lib/agent-docker/ready
```

**2. Завершить работу агента и остановить гостя.** Выйти из Claude, отсоединиться по `Ctrl+]`,
затем `make vm-stop VM=vm-02` и убедиться по `make vm-list`, что гость остановлен. Остановка
штатная: выключение идёт изнутри гостя.

**3. Обновить образ на хосте и проверить, что старый диск с ним загружается.**

```sh
make vm-setup VM=vm-02
make vm-sessions-check VM=vm-02   # по-прежнему old-image: диск ещё не тронут
make vm-stop VM=vm-02
```

Пересборка обновляет контейнер, а не гостя: `write_files` и `runcmd` cloud-init применяются один
раз на `instance-id`, и менять `instance-id` нельзя — на копии старого диска это сгенерировало
новый ключ хоста ED25519 и сменило его отпечаток. Поэтому гостевые файлы ставятся следующим
шагом, вручную и по одному.

**4. Смонтировать корень остановленного гостя на хосте.** Корень монтируется в контейнере того же
образа: в нём есть `qemu-nbd`, и базовый образ доступен по тому пути, который записан в
`disk.qcow2` как backing file. Права root нужны на хосте, внутри гостя — нет.

```sh
sudo modprobe nbd max_part=8
docker run --rm -it --privileged --device /dev/nbd0 \
  --mount "type=volume,src=agent-docker-v2-base,dst=/images" \
  --mount "type=bind,src=$PWD/.v2-state/vm-02,dst=/guest" \
  --mount "type=bind,src=$PWD/v2,dst=/scripts,readonly" \
  agent-docker-v2:local bash
```

Внутри контейнера:

```sh
qemu-nbd --connect=/dev/nbd0 /guest/disk.qcow2
mkdir -p /mnt/guest && mount /dev/nbd0p1 /mnt/guest
ls /mnt/guest/etc/ssh/ssh_host_ed25519_key    # корень тот самый, ключ на месте
```

**5. Поставить канал сессий офлайн.** Сначала проверка, потом установка — установщик отказывается
работать, если на целевом пути подложена символическая ссылка или не обычный файл:

```sh
bash /scripts/install-sessions-guest.sh --check   --root /mnt/guest   # покажет, чего нет
bash /scripts/install-sessions-guest.sh --install --root /mnt/guest   # пять файлов и включение
bash /scripts/install-sessions-guest.sh --check   --root /mnt/guest   # всё «на месте» и «включён»
```

Записываются ровно пять файлов: служба, юнит, правило udev, файл `tmpfiles` с каталогом сокета и
`profile.d` с его путём. Повторный запуск при совпадающем содержимом не пишет ничего.

**6. Поставить tmux однократной службой.** Пакет ставится внутри гостя, из того же списка
источников, и только один раз. Файл создаётся в смонтированном корне:

```sh
cat > /mnt/guest/etc/systemd/system/atrice-tmux-install.service <<'UNIT'
[Unit]
Description=Atrice: однократная установка tmux
# Условие делает шаг идемпотентным: при уже установленном tmux служба не
# делает ничего ни сейчас, ни при следующих загрузках.
ConditionPathExists=!/usr/bin/tmux
Wants=network-online.target
After=network-online.target agent-docker-prepare.service

[Service]
Type=oneshot
# Источники только разрешённые: список гостя, sources.list.d отключён.
ExecStart=/usr/bin/apt-get -o Dir::Etc::sourcelist=/etc/apt/agent-docker.list -o Dir::Etc::sourceparts=- -o Acquire::Retries=0 update
ExecStart=/usr/bin/apt-get -o Dir::Etc::sourcelist=/etc/apt/agent-docker.list -o Dir::Etc::sourceparts=- -o Acquire::Retries=0 install -y --no-install-recommends tmux
StandardOutput=journal+console
StandardError=journal+console

[Install]
WantedBy=multi-user.target
UNIT
ln -s /etc/systemd/system/atrice-tmux-install.service \
  /mnt/guest/etc/systemd/system/multi-user.target.wants/atrice-tmux-install.service
sync && umount /mnt/guest && qemu-nbd --disconnect /dev/nbd0 && exit
```

Ссылка в `multi-user.target.wants` — это ровно то, что делает `systemctl enable`, поэтому systemd
на хосте для включения не нужен.

**7. Запустить гостя и проверить результат.**

```sh
make vm-up VM=vm-02
make vm-sessions-check VM=vm-02
```

Ожидается `state: empty`, `tmux` — версия пакета, `socket: absent` (сессий ещё нет, и это не
отказ), `console: free`. Внутри гостя проверка в обратную сторону:

```sh
tmux -V
systemctl is-active atrice-sessions.service
systemctl status atrice-tmux-install.service   # inactive, условие больше не выполняется
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub   # отпечаток совпадает с шагом 1
cat /var/lib/agent-docker/ready                    # прежняя строка
```

Отпечаток ключа и строка готовности обязаны совпасть с записанными на шаге 1, а
`make vm-profile VM=vm-02` — с `/tmp/vm-02.profile.before` с точностью до времени запуска. Если
что-то из этого разошлось, дальше не идти: это признак перепровижинирования, а не установки
канала.

**8. Убрать однократную службу (необязательно).** Она уже ничего не делает: условие
`ConditionPathExists=!/usr/bin/tmux` не выполняется при установленном tmux. Если оператор хочет
убрать её совсем, это делается тем же монтированием на остановленном госте: удалить юнит и ссылку
включения. Ни файлы канала, ни tmux при этом не затрагиваются.

Откат: до шага 5 ничего в госте не менялось — достаточно запустить его обратно. После шага 5
откат — удаление тех же пяти файлов и ссылки включения на смонтированном корне; удалённый канал
возвращает гостя в состояние `old-image`, и консоль по `c` работает во всех случаях.

Флаги можно ставить в любом месте команды: `atrice logs vm-02 --follow` и `atrice logs --follow vm-02` равнозначны.

Вывод подсвечивается собственной палитрой: янтарный `#E08D3C` для имени гостя и приглашения, приглушённый `#8A8578` для подсказок и заголовков, зелёный `#5FA97F` для работающего гостя, красный `#C85A54` для ошибок и повреждённой настройки. В терминале с поддержкой 24-битного цвета берутся точные значения, иначе — ближайшие цвета из 256. Раскраска отключается переменной `NO_COLOR`, при `TERM=dumb` и при выводе не в терминал, например в файл или конвейер.

Каталог проекта определяется автоматически: сначала `--root`, затем `AGENT_DOCKER_ROOT`, затем поиск `v2/manage.sh` рядом с бинарником и в текущем каталоге с подъёмом к корню. Переменные `V2_STATE_DIR` и `V2_PROJECT_PREFIX` действуют так же, как для `make`.

Токен Git и пароль прокси вводятся в ответ на запрос `manage.sh` и остаются на хосте. `atrice` не принимает их в аргументах, не печатает и не сохраняет: в списке и в `atrice status` показываются только провайдер, репозиторий, режим и разрешённая ветка.

## Команды с хоста

| Команда | Действие |
| --- | --- |
| `make vm-list` | Показать состояние настроенных гостей. |
| `make vm-git-status VM=vm-02` | Показать настройку Git-шлюза гостя без токена. |
| `make vm-up VM=vm-02` | Запустить гостя после проверки его прокси. Без `VM` обрабатывает настроенных гостей в диапазоне `VM_COUNT`. |
| `make vm-stop VM=vm-02` | Послать гостю штатную команду выключения и остановить его шлюз. |
| `make vm-console VM=vm-02` | Открыть локальную консоль гостя. |
| `make claude-auth VM=vm-02` | Запустить вход в аккаунт Claude. |
| `make claude VM=vm-02` | Открыть Claude в `~/projects` гостя. |
| `make claude VM=vm-02 PROJECT="my-project" RESUME="Название сессии"` | Открыть существующий проект и продолжить сессию. |
| `make claude-logout VM=vm-02` | Выйти из аккаунта Claude внутри гостя. |
| `make vm-logs VM=vm-02 LOG_SERVICE=proxy LOG_TAIL=100` | Показать журналы контейнеров гостя. `LOG_FOLLOW=1` следит за новыми строками. |
| `make vm-profile VM=vm-02` | Показать `profile.json` запущенного гостя. |
| `make vm-remove VM=vm-02` | Удалить контейнеры и сеть гостя. Имя обязательно: гость по умолчанию не подставляется. `DISK_KEEP=0` удаляет также диск и каталог состояния. |

При подключении к консоли показывается хвост журнала гостя: после возврата в сессию видно, что происходило, пока консоль была отключена.

Если `VM` опущена в одиночной команде, выбирается `vm-01`. Для первого входа откройте ссылку из терминала в браузере на своём компьютере и введите код в консоли, если сайт его покажет. Чтобы отсоединиться от консоли гостя, нажмите `Ctrl+]`. Если Claude продолжает работать, вернитесь в него через `make vm-console`. После выхода из Claude консоль автоматически откроет новую оболочку. Если вы вводили команды вручную через `make vm-console`, выполните `exit` в Bash и отсоединитесь через `Ctrl+]`. После этого можно снова вызвать `make claude`, `make claude-auth` или `make claude-logout`.

## Проекты и хранение данных

Клонируйте проекты в `~/projects` внутри выбранной VM. При необходимости добавьте домен Git-сервера в список гостя. У каждого гостя свой постоянный Docker-том с диском `qcow2`. Базовый Debian общий и подключается только для чтения. Остановка гостя сохраняет рабочие файлы, авторизацию и сессии. Сделайте резервную копию тома перед его удалением.

Версионированный профиль `profile.json` хранится в томе гостя рядом с диском. Для новых VM он фиксирует при первом запуске UUID, MAC, серийные номера SMBIOS (system, board, chassis) и серийный номер диска. При обновлении существующих гостей сохраняются прежние параметры виртуального оборудования: профиль без серийных номеров их не получает, а диск, созданный до появления профиля, сохраняет значения QEMU по умолчанию. Производитель и модель остаются стандартными для QEMU. Нужна сборка QEMU с поддержкой seccomp: без неё `-sandbox on` не принимается и VM не запустится, поэтому её наличие проверяется при сборке образа.

Способ подключения данных cloud-init тоже фиксируется при создании гостя. Новый гость получает их как `virtio-blk`, а созданный ранее сохраняет прежний CD-ROM: скрипт подготовки попадает внутрь один раз через `write_files` cloud-init, у такого гостя он продолжает монтировать `/dev/sr0`, и без этого устройства гость перестал бы готовиться к работе. Выбор хранится в `profile.json` рядом с остальным виртуальным оборудованием, поэтому он сохраняется и при перезапуске, и при восстановлении тома из резервной копии. У гостя, созданного прошлой версией, значение дописывается в профиль при первом запуске. Устройство с данными cloud-init гость ищет по метке `cidata`: сначала по ссылке udev, затем через `blkid`. В профиле есть имя VM, ресурсы и ссылка на конфигурацию прокси. Сам адрес upstream и его учётные данные хранятся в файле `upstream` у шлюза.

## GitHub и GitLab для гостевой VM

В меню Atrice на хосте клавиша `g` показывает настройку шлюза и позволяет её
изменить. Укажите репозиторий, провайдера, ветки чтения и при необходимости
ветку записи. Сам токен вводится отдельным скрытым запросом на хосте.

Для GitLab, который доступен с хоста через корпоративную сеть, можно
включить отдельный режим чтения. Сначала назначьте репозиторий и ветки через
`g`. Затем на хосте выполните:

```sh
atrice git host-sync vm-05
atrice git host-activate vm-05
```

Первая команда обращается к GitLab напрямую с проверкой TLS средствами
хоста и публикует очищенную копию. Вторая пересоздаёт только контейнер
шлюза. Гость продолжает клонировать `http://git.agent-docker.test/project.git`.
Для обновления веток снова вызовите `atrice git host-sync vm-05`.
По умолчанию зеркало работает на чтение. Если в настройке есть ветка
записи, запустите в отдельном терминале хоста `atrice git host-writer vm-05`.
Агент отправляет изменения командой `git push origin HEAD:work`. Успех
означает, что GitLab принял коммиты и хост обновил зеркало. В режиме
фильтрации нельзя менять файлы, исключённые правилами или переписанные
при очистке. После остановки обработчика старое зеркало продолжает
отдаваться для чтения. Чтобы вернуться к обычному режиму, выполните `atrice git host-disable vm-05` и пересоздайте контейнер
шлюза. До пересоздания зеркало хоста недоступно.

Чтобы проверить, что получит агент, выполните на хосте `atrice git audit vm-05`
или откройте `g` в меню ВМ с опубликованным зеркалом. Проверка проходит по
всей доступной истории, включая версии удалённых файлов. В отчёте указаны
файл, строка, коммит и сработавшее правило. Значения найденных секретов не
печатаются. Бинарные файлы и объекты больше 2 МиБ перечислены как пропуски.

Правила `audit-rules.json` и полный отчёт `audit-report.json` находятся в
хостовом каталоге `git-host-private` выбранной ВМ. Домен и путь назначенного
репозитория проверяются автоматически. В правилах можно задать дополнительные
`domains` и `markers`, а также шаблоны `ignored_paths`. Аудит только сообщает о
находках и не меняет опубликованные данные.

Для фильтрации содержимого добавьте в хостовый каталог `git-host-private`
файл `filter-rules.json`. Поле `exclude` содержит шаблоны путей. Поле
`replace` содержит буквальные пары `from` и `to` для текстовых файлов.
Правила действуют для всех коммитов, которые выдаются гостю. Например:

```json
{
  "exclude": ["CHANGELOG.md", ".pre-commit-config.yaml"],
  "replace": [{"from": "git.example.com", "to": "git.example.invalid"}]
}
```

После `atrice git host-sync vm-05` непроверенная копия остаётся на хосте.
Публикация проходит только если аудит не нашёл запрещённых данных и не
пропустил файлы. Исключения `ignored_paths` из обычного аудита при этом
отключены. При первом включении прежняя неочищенная публикация снимается.
После изменения правил клонируйте репозиторий заново в отдельный каталог.
Прежний клон может хранить старые Git-объекты даже после `git fetch`.

Чтобы дать агенту историю нескольких веток, назначьте им нейтральные имена.
Например, с хоста:

```sh
atrice git vm-02 --repo owner/repository --write agent/task \
  --read-branch reference=release/test --read-branch next=release/next
```

В госте можно выполнить `git fetch` и перенести коммит из `origin/reference`
в `work` через `git cherry-pick`. Для публикации изменений подготовьте их
поверх актуальной `origin/work` и отправьте через `git push origin HEAD:work`.
Если вершина `work` изменилась, сначала выполните `git fetch` и
`git rebase origin/work` для локальных неопубликованных коммитов.

При заданных ветках чтения шлюз сохраняет общих предков и связи между
коммитами, заменяет идентификаторы коммитов, авторов, даты и сообщения
upstream. Гость видит `main`, выбранные псевдонимы и `work`, если включена
запись. Теги, реальные имена веток и служебные файлы скрыты. Содержимое
исторических версий файлов доступно так же, как содержимое текущего снимка.
Без веток чтения действует прежний режим снимков. После смены набора веток
сделайте новый клон, предварительно сохранив неопубликованные изменения.

С хоста назначьте VM один репозиторий и введите отдельный токен GitHub, ограниченный этим репозиторием. Для клонирования и fetch достаточно доступа на чтение. Для push нужны разрешение токена на запись и явное назначение одной ветки через `GIT_WRITE=1 GIT_WRITE_BRANCH=test/gateway-write`. Шлюз отклоняет запросы к другим веткам, тегам и удаление ветки. При обновлении старой настройки повторно укажите разрешённую ветку для включения записи.

```sh
make vm-git VM=vm-02 REPO=owner/repository
```

Для GitLab, включая self-managed, укажите провайдера и адрес сервера. `REPO` задаёт полный путь проекта с группой и подгруппами:

```sh
make vm-git VM=vm-02 GIT_PROVIDER=gitlab GIT_URL=https://gitlab.example.com REPO=group/subgroup/project
make vm-git VM=vm-02 GIT_PROVIDER=gitlab GIT_URL=https://scm.example.com/gitlab REPO=group/project GIT_WRITE=1 GIT_WRITE_BRANCH=agent/task-1
```

Адрес GitLab принимается только по `https`, с DNS-именем хоста в нижнем регистре, без IP-адреса и без хостов `github.com`, без логина, пароля, параметров и сегментов `.` и `..`. Допускаются порт до 65535 и префикс пути, одна завершающая косая черта отбрасывается. Путь проекта состоит из 2–20 сегментов. Для GitLab подходит токен сервисного пользователя, project или group access token с правом `read_repository`, а для записи также `write_repository`. Шлюз передаёт его GitLab как пароль пользователя `oauth2`. Без `GIT_PROVIDER` используется GitHub, ранее сохранённые настройки GitHub продолжают работать. Провайдер, адрес, путь проекта и токен хранятся только на хосте в `repository.json`, путь проекта GitLab записывается в поле `project`. Если работающий шлюз собран из версии без поддержки GitLab, `make vm-git` и `make vm-setup` останавливаются до записи настройки и просят выполнить `make vm-stop` и `make vm-setup`. Выход к GitLab идёт через upstream этой VM со стандартной проверкой TLS, поэтому серверу нужен публично доверенный сертификат. Для записи достаточно проектного токена; права на ветку дополнительно ограничивают правила protected branches в GitLab. Гость в обоих случаях работает с тем же адресом `http://git.agent-docker.test/project.git` и видит нейтральные имена веток. Смена провайдера или адреса считается сменой назначения.

Репозиторий можно назначить и при создании гостя:

```sh
make vm-setup VM=vm-02 REPO=owner/repository
make vm-setup VM=vm-02 REPO=owner/repository GIT_WRITE=1 GIT_WRITE_BRANCH=test/gateway-write
```

Без `REPO` команда `vm-setup` работает как раньше и Git-шлюз не настраивает. С `REPO` она после проверки прокси, KVM и сборки образа, но до запуска VM, запрашивает токен тем же скрытым вводом, что и `vm-git`, и создаёт настройку шлюза. По умолчанию доступ только на чтение. Если настройка уже есть, повтор с тем же репозиторием, режимом записи и веткой использует её без повторного ввода токена. При другом репозитории, режиме или ветке, а также если сохранённую настройку не удаётся прочитать, `vm-setup` останавливается до запуска VM, не меняет сохранённую настройку и показывает команду `make vm-git` для замены. Токен хранится только в `.v2-state/vm-XX/git/repository.json` и не записывается в `.env`.

Проверить сохранённую настройку можно так:

```sh
make vm-git-status VM=vm-02
```

Команда показывает репозиторий, режим и разрешённую ветку для записи либо сообщает, что шлюз не настроен. Она только читает `repository.json` тем же парсером, что и `vm-setup`: VM не запускается и не перезапускается, к GitHub запросов нет. Токен не выводится, в том числе при повреждённой настройке. Если запись включена, но ветка недопустима, команда показывает режим только чтения: шлюз такой push отклоняет. Как и другие цели Make, при отсутствии `.env` команда создаёт его из шаблона.

При первом включении шлюза на работающей VM закончите текущую сессию, выполните `make vm-stop VM=vm-02`, затем `make vm-setup VM=vm-02`. Сохранённый диск используется повторно. В госте выполните:

```sh
git clone http://git.agent-docker.test/project.git
```

Гость работает с обезличенной копией в шлюзе. Без дополнительных веток чтения действует режим снимков. При каждом clone, fetch и push шлюз забирает ветку по умолчанию и, если включена запись, назначенную ветку у GitHub или GitLab по HTTPS через upstream этой VM. Из них он строит снимок без истории: один коммит от `agent-docker <agent-docker@localhost>` с фиксированной датой и сообщением «Снимок репозитория». Новые изменения у провайдера появляются как следующий такой же коммит. Из снимка удаляются `.github/`, `.gitlab/`, `.gitlab-ci.yml`, файлы `CODEOWNERS` в любом каталоге, `.mailmap`, `.git-blame-ignore-revs`, `.gitmodules` и ссылки на подмодули. Гостю видны только ветки `main` и, если включена запись, `work`. Настоящее имя ветки записи из `GIT_WRITE_BRANCH` знает только шлюз: оно не попадает в ref'ы, коммиты и сообщения зеркала. Содержимое файлов при этом сохраняется без изменений, поэтому имя ветки, упомянутое внутри файлов проекта, остаётся видно. Для каждого назначения, то есть репозитория и ветки записи, шлюз держит отдельное зеркало. После `make vm-git` с другим назначением прежнее зеркало удаляется при первом обращении гостя, запросы без предварительного обновления отклоняются, а push в копию прежнего назначения не принимается. Запрос, начатый до смены назначения, может завершиться с прежними данными или прерваться: повторите его. В госте, клонировавшем репозиторий до обновления шлюза или до смены назначения, выполните новый `git clone`. Имена и почта авторов, сообщения коммитов, служебные ref'ы, ответы и сообщения провайдера до гостя не доходят. Токен хранится на хосте и доступен только шлюзу.

Push принимается только в ветку `work`, только продолжением её истории, без коммитов слияния и без изменения удалённых из снимка файлов. Шлюз переносит каждый коммит агента в назначенную ветку у провайдера как отдельный коммит от `agent-docker` поверх её текущей вершины и отправляет провайдеру. Сообщения коммитов агента сохраняются. Если ветка у провайдера изменилась или изменения конфликтуют, push отклоняется: выполните `git pull --rebase` и повторите. Ветка записи, которой ещё нет у провайдера, начинается со снимка `main`, следует за его обновлениями и создаётся у провайдера первым push от актуальной вершины `main`. Если `main` у провайдера обновился после последнего fetch гостя, push отклоняется: выполните `git pull --rebase`, коммиты агента сохранятся поверх нового снимка. Уже существующая у провайдера ветка видна гостю отдельным снимком без общей истории с `main`. Если ветку удалить у провайдера, в копии она снова начнётся со снимка `main`. Размер одного push ограничен 256 МБ, сжатое тело push не принимается. Локальные `status`, `diff` и `commit` выполняются в госте. Права токена и правила защиты веток у провайдера продолжают действовать. Обезличивается история и служебные данные, но не содержимое файлов: имена и адреса в коде и документации остаются.

## Проверка сети из гостя

Скрипт `v2/tests/isolation_probe.py` запускается внутри тестовой VM. Передайте URL и адрес шлюза для положительной проверки, адреса для запрета TCP и DNS, а для UDP укажите тестовый echo-сервис. Адаптер стенда должен подтвердить доступность контрольных сервисов с разрешённой стороны. Скрипт возвращает JSON и ненулевой код при нарушении. Проверка DNS определяет наличие рабочего ответа. Для проверки утечки самого запроса дополнительно нужна фиксация пакетов на границе сети.

## Журнал SNI

Журнал решений HTTPS-шлюза выключен по умолчанию. Чтобы включить его, перезапустите гостя с переменной:

```sh
make vm-stop VM=vm-02
make vm-up VM=vm-02 GATEWAY_SNI_LOG=1
docker compose --project-name agent-docker-v2-vm-02 logs proxy
```

Для каждого решения по HTTPS-соединению шлюз пишет одну JSON-строку только с тремя полями: время, домен из SNI и решение `allow` или `deny`. Соединение без TLS или со слишком большим приветствием записывается как `deny` с пустым доменом. Соединения, закрытые до полного ClientHello или по таймауту, не записываются. Адреса, порты, пути и содержимое не записываются. Журнал ротируется Docker: не более трёх файлов по 1 МБ. При следующем запуске без `GATEWAY_SNI_LOG=1` журнал снова выключается, если переменная не экспортирована в оболочке. Журнал помогает определить фактический минимальный список доменов. Это диагностика, а не аудит: содержимое записей задаёт гость, и потоком соединений он может вытеснить старые записи из ротации.

## Модель угроз

Изоляция ограничивает, куда гость может подключаться, и не ограничивает, какие данные он передаёт через разрешённые каналы.

Схема защищает от следующего:

- прямого выхода гостя в сеть мимо шлюза: IPv4, IPv6, UDP, включая DNS и QUIC, ICMP, сервисов на loopback контейнера QEMU и соседних VM. Запрет обеспечивают внутренняя сеть Compose и правило nftables контейнера VM, а не настройки QEMU user networking. Проверяйте его скриптом `isolation_probe.py`;
- доступа гостя к адресу и учётным данным upstream и к токену Git: они есть только у контейнера шлюза;
- обращения к репозиториям, кроме назначенного, и записи в другие ветки, теги и удаления веток;
- раскрытия гостю истории, авторов, служебных ref'ов и сообщений Git-провайдера;
- общих идентификаторов виртуального оборудования у новых гостей. У существующих гостей сохраняются прежние значения. `machine-id` и SSH-ключи создаёт сам гость при первой загрузке;
- вложенной виртуализации внутри гостя: QEMU запускается с `-cpu host,-vmx,-svm`;
- части приёмов расширения прав самого QEMU после запуска. Он работает с `-sandbox on`, где запрещены устаревшие системные вызовы, `set*uid`, `set*gid`, запуск новых процессов и управление приоритетами. Это список запретов, а не разрешений, и часть из них уже закрыта профилем seccomp Docker. Фильтр устанавливается без `CAP_SYS_ADMIN` только потому, что `setpriv` ставит `no-new-privs` и обнуляет все capability. Отказ в запрещённом вызове убивает QEMU по `SIGSYS`: если VM внезапно исчезла, ищите `seccomp` в `docker compose logs` и в `dmesg` хоста.

Схема не защищает от следующего:

- Передача данных через разрешённые каналы. Всё, что доступно в госте, включая OAuth-токен Claude и рабочие файлы, агент может отправить в API Anthropic, на другой разрешённый домен или в разрешённую ветку Git. Помещайте в гостя только данные, допустимые для агента и провайдера, выдавайте токен с минимальными правами и включайте защиту веток у Git-провайдера.
- Обход по имени домена. Шлюз сверяет только SNI и не видит HTTP-заголовок Host внутри TLS. Если разрешённый домен обслуживает CDN, допускающая domain fronting, через него можно обратиться к другому сайту этой CDN. Держите список доменов минимальным.
- Уязвимости QEMU, KVM и ядра хоста. Граница между гостем и хостом проходит через KVM и контейнер Docker на общем ядре. Контейнер не добавляет независимой границы: ядро у них общее. Модель устройств сокращена до virtio плюс неизбежная периферия чипсета i440FX: контроллер IDE, PS/2, RTC, таймеры, PCI-бридж и `fw_cfg` остаются, поскольку входят в саму машину. Убрано ATAPI-устройство CD-ROM, а не контроллер IDE. Песочница и минимум устройств сокращают поверхность, но не заменяют гипервизор на выделенной машине. Сам QEMU работает с UID 0 внутри контейнера; запуск под непривилегированным пользователем остаётся улучшением.
- Компрометация шлюза. Контейнер шлюза имеет выход в сеть, учётные данные upstream и токен Git.
- Сохранение компрометации гостя. Диск гостя постоянный, поэтому изменения, внесённые агентом, переживают перезапуск. Для чистого состояния создайте нового гостя.
- Вывод консоли гостя. `make vm-console` и `make claude` передают в терминал хоста данные, которые формирует гость, включая управляющие последовательности.
- Метаданные в содержимом файлов. Шлюз удаляет известные служебные файлы, но имена, адреса и ссылки внутри кода и документации остаются видны гостю.
- Определение виртуализации. Уникальные серийные номера разделяют гостей между собой, а скрытие факта виртуализации и подмена производителя в задачи проекта не входят.
