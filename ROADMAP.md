# Roadmap agent-docker

Цель проекта - дать пользователю единый терминал Linux для запуска изолированных окружений разработки, работы с Claude Code и Codex и переключения между их сессиями.

## v0.1.0. Базовое окружение

Ветка `release/v0.1.0` содержит MVP на Docker Compose и KVM. Текущий способ работы описан в [руководстве](GUIDE.md).

- `make` или `make vm-setup` с хоста проверяет KVM, ресурсы и доступность прокси, затем готовит гостя Debian и устанавливает Claude Code. Повторная настройка сохраняет диск.
- У каждой VM свой диск, проектные файлы, авторизация и история сессий. Проекты хранятся внутри гостя. На одной Linux-машине можно поднять несколько гостей с отдельными настройками CPU, RAM, диска и прокси.
- Сетевой шлюз расположен вне гостя. Прокси проверяется до установки. HTTP и HTTPS через шлюз ограничены списком разрешённых доменов. Адрес и учётные данные upstream остаются в конфигурации шлюза, а внутри VM приложения используют обычные HTTP и HTTPS.
- Make позволяет управлять гостями, открывать консоль, запускать Claude Code, входить, выходить и возобновлять сохранённую сессию. `Ctrl+]` отсоединяет терминал, а `make vm-console` подключается обратно к работающему процессу.

На KVM проверены установка через прокси, повторный запуск с тем же диском и возврат к работающей консоли. В пилоте предстоит проверить вход с реальной подпиской и одновременную работу двух VM с разными upstream-прокси. Изоляцию оцениваем по разделению дисков, процессов, сетей и учётных данных гостей. Определение устройства и связывание аккаунтов относятся к политике провайдера.

## Проверка изоляции KVM и прокси

Критерии перед пилотом по issue #2 и #3. Текущий MVP использует отдельную внутреннюю сеть Compose для каждой VM, QEMU user networking и отдельный HTTP/HTTPS-шлюз. В госте разрешённые имена направляются к шлюзу через `/etc/hosts`. Адрес шлюза виден из гостя. Адрес upstream и его учётные данные находятся на стороне шлюза.

- Проверить на двух VM, что гость не может подключиться к соседней VM, loopback контейнера QEMU, службам Linux-хоста и частным адресам вне разрешённых сервисов. Проверять из самой VM, в том числе по IP.
- Проверить исходящий трафик по IPv4 и IPv6, обычный DNS по UDP и TCP, UDP/443 (QUIC) и прямые подключения по IP. Убедиться, что запросы к неизвестным доменам не уходят к DNS хоста и что прямой выход закрыт при остановленном шлюзе, недоступном upstream и ошибке авторизации прокси.
- Назначить двум гостям разные прокси и сверить их внешние IP через разрешённый сервис. После смены прокси у одной VM повторить тест для обеих. Проверить отсутствие параметров и учётных данных upstream в переменных окружения и файлах гостя.
- Проверить, что общий базовый образ подключён только для чтения. У каждой VM должны быть собственный диск и устойчивые идентификаторы. Проверять UUID VM по QMP и отдельно SMBIOS UUID из гостя, MAC, серийный номер диска, `machine-id`, hostname и состояние CLI. Генерировать идентификаторы один раз при создании VM. При создании нового гостя проверить отсутствие унаследованной авторизации, сессий и ключей. Для включённого SSH проверить отдельные ключи хоста. При рестарте существующей VM состояние должно сохраняться.
- Выделить проверяемую политику сети отдельно от создания VM. Решение о замене сетевой схемы принимать по результатам этих проверок. В пилот входит проверяемая изоляция и контроль исходящего доступа. Различия TLS-профилей, TTL, MTU и географии не входят в критерии изоляции.

### Результаты первого прогона на Compose

Два гостя Debian с одним upstream и отдельными шлюзами получили разные `machine-id`, имена и SSH-ключи, и одинаковый MAC. QEMU сообщил нулевой UUID у обеих VM. SMBIOS UUID внутри гостя и серийный номер диска ещё предстоит подтвердить.

Из обеих VM сработал разрешённый HTTPS. Прямое подключение к тестовым публичным адресам по IPv4 и IPv6 и подключение к соседнему шлюзу не прошли. При этом гость смог подключиться к тестовым сервисам на loopback своего контейнера QEMU по TCP и UDP. Встроенный DNS QEMU ответил `SERVFAIL` по TCP и UDP. Этот ответ сам по себе не подтверждает, что DNS-запрос остался внутри сети.

Выключение шлюза и недоступность upstream остановили разрешённый HTTPS в затронутой VM. При выключенном шлюзе соседняя VM продолжила работу. После рестарта сохранились файл на диске и `machine-id`. Сетевой прогон не зависел от установки агента.

До пилота закрыть доступ к loopback контейнера QEMU, проверить фактический маршрут DNS и закрепить уникальные идентификаторы виртуального оборудования. В отдельном прогоне с двумя разными upstream подтверждены разные внешние IP непосредственно из гостей. Прямой TCP/443 к контрольному публичному IP был недоступен в обеих VM. Эти проверки войдут в общий набор для обеих платформ.

## Kubernetes и KubeVirt

KubeVirt рассматриваем как второй способ запуска для заказчиков с Kubernetes или несколькими узлами. В `v0.1.0` сохраняем текущий способ запуска на Docker Compose и KVM. На одном Linux-хосте Compose остаётся базой для пилота. Интерфейс CLI должен сохранять сценарии создания, запуска, остановки и подключения к консоли независимо от способа запуска.

- Использовать общий генератор профилей для Compose и KubeVirt. Генератор один раз создаёт версионированный JSON с `vm_id`, UUID, MAC, ресурсами и ссылкой на настройки прокси. При повторном запуске загружается сохранённый профиль. Каждая платформа связывает этот профиль со своим диском и сетевой политикой. Токены и пароли остаются у соответствующего шлюза.
- Оставить в собственном CLI одинаковые операции создания, запуска, остановки и подключения к VM. Адаптер Compose преобразует профиль в настройки QEMU. Будущий адаптер KubeVirt преобразует его в манифест `VirtualMachine` и запускает те же проверки изоляции. При удалении VM пользователь явно выбирает, сохранять ли диск.
- Для пробного развёртывания проверить на двух VM KVM на узле, создание через `VirtualMachine`, консоль через `virtctl`, загрузку Debian-образа и сохранение диска через PVC или DataVolume. Для существующего Compose-диска оценить импорт отдельно на копии.
- Проверить Kubernetes-сеть с CNI, который применяет `NetworkPolicy`. Запретить исходящий трафик по умолчанию и разрешить каждой VM только её шлюз и явно утверждённые сервисы. Шлюз отвечает за список доменов и подключение к выделенному upstream. У стандартной NetworkPolicy есть исключение для трафика к своему узлу. Блокировку доступа к узлу проверять отдельно. Из гостя проверить применение политики, поведение DNS и отказ шлюза, в том числе после пересоздания Pod.
- Сравнить с Compose по времени подготовки гостя, фоновому потреблению ресурсов, сложности настройки и результатам одних и тех же тестов. Выбирать KubeVirt для боевого развёртывания после подтверждения преимуществ на инфраструктуре заказчика. Перед масштабированием повторить приёмку на трёх VM.

### Общие тесты изоляции

- Один набор проверок запускается внутри гостевой Debian и выдаёт одинаковые результаты для Compose и KubeVirt. Он проверяет разрешённое HTTPS-подключение, отказ прямого выхода, DNS, доступ к соседям и узлу, изоляцию диска, стабильность профиля после рестарта и отказ прокси. Фикстуры используют тестовые сервисы и выдают результат без секретов.
- Адаптер каждой платформы готовит VM, возвращает сведения о запущенных гостях и тестовых адресах, выполняет команды из гостя через его консоль, управляет тестовым шлюзом и очищает временные ресурсы. Утверждения о поведении сети и сохранности состояния одинаковы для обеих платформ.
- Часть проверок выполняется на минимальном Debian без установки агента. Установка и авторизация Claude Code и Codex проходят отдельным сквозным тестом. Это позволяет повторять сетевые тесты при изменении инфраструктуры независимо от доступности пакетов агентов.

## Первый выпуск Linux CLI

Пользователь скачивает `agent-docker` и работает из одного полноэкранного терминала. Первый целевой хост - Linux `amd64` с Docker, Compose и доступом к KVM.

- Собрать CLI на Go и публиковать бинарник, контрольную сумму и примечания к выпуску в GitHub Releases. Исходники остаются в этом репозитории. Скрипты и шаблоны поставляются вместе с приложением, чтобы его можно было запустить из любого каталога.
- Переиспользовать текущие Make-цели и скрипты. Добавить проверку зависимостей, создание VM, выбор ресурсов и ручного прокси, список, запуск и остановку VM.
- Показать в меню окружения и открывать родную консоль агента внутри приложения. Сценарий первого выпуска - создать гостя, открыть Claude Code, вернуться в меню, выбрать другую VM и подключиться обратно к первой. На этом этапе достаточно одного открытого терминала на VM.
- Добавить установку и запуск Codex в госте с сохранением ограничений на исходящую сеть.

## Сессии и панель статуса

- Хранить привязку сессии к VM, агенту и проекту. Открытые сессии подключать к живому процессу, сохранённые возобновлять по ID. После выключения VM живой процесс завершается, а сохранённая история остаётся на диске.
- Для нескольких живых сессий в одной VM выделять каждой свой псевдотерминал. Проверить переключение, передачу клавиш, изменение размеров окна и восстановление после переподключения.
- В панели показывать VM, проект, имя сессии, агент, версию, модель, состояние авторизации и, когда доступны, тариф, долю остатка лимита и время сброса. Отмечать время последнего обновления или отсутствие данных. Лимиты относятся к аккаунту или провайдеру, через которого работает агент.
- Для Claude Code брать модель, сессию и доступные лимиты из `statusline`, состояние входа - из `claude auth status`. Автоматическое определение тарифа зависит от доступных данных. Вход пользователь проходит в штатном CLI внутри гостя.
- Для Codex использовать официальный App Server для списка и восстановления сессий, а также данных о модели, тарифе и лимитах там, где их возвращает выбранный способ авторизации. Передавать в панель только поля для отображения. Учётные данные остаются внутри гостя.

## Git-шлюз

- Вынести шлюз и токены проектов за пределы VM. Пользователь назначает репозитории выбранному окружению. Гость получает рабочую копию и адрес шлюза, а также видит данные и историю выданного репозитория.
- `status`, `diff` и `commit` выполняются локально. `clone`, `fetch` и `push` идут через шлюз. Личные учётные данные и настройки Git пользователя остаются за пределами гостя.
- Начать с одного Git-провайдера. Шлюз проверяет, какой VM разрешён доступ к репозиторию. По умолчанию выдаётся чтение, запись включается отдельно. На пилоте проверить запрет доступа к чужому репозиторию и запрет записи без разрешения.

## Задачи, PR и релизные ветки

Рабочий цикл состоит из двух ролей. Исполнитель получает задачу, выполняет её в своём окружении и отправляет изменения. Планировщик ведёт список задач по роадмапу, сверяет результат с планом и собирает выпуск. Инвариант Git-шлюза сохраняется: токен и API провайдера остаются за его пределами, а гость обращается к зеркалу только по маршрутам Git Smart HTTP. API провайдера в список разрешённых доменов не входит.

- Доставлять очередь задач в гостя через зеркало как файлы в отдельной ветке только для чтения. Шлюз читает задачи по API провайдера и обновляет эту ветку. Гость не получает новых сетевых разрешений и не видит токен.
- Выдавать задачу на стороне шлюза, а не выбором агента. Одна задача закрепляется за одним окружением, повторная выдача запрещена. Без этого два гостя возьмут одну задачу.
- Передавать отчёт о работе трейлерами коммита. Шлюз разбирает их при экспорте, пишет комментарий, закрывает задачу и открывает PR или MR. Агент по-прежнему выполняет только `push`.
- Расширить запись с одной ветки `work` до пространства имён с ветвью на задачу. Состояние зеркала уже хранится по ветке. Запрет перезаписи истории, удаления веток и коммитов слияния сохраняется.
- Различать авторство агентов в PR. Сейчас шлюз заменяет личность коммитов на свою, поэтому вклад разных окружений неотличим. Решить, что именно подставляется, до включения второй роли.
- Оставить сборку релизной ветки за пределами гостя. Ей нужны полная история и коммиты слияния, а зеркало выдаёт сплющенный снимок и запрещает слияния. Эта роль выполняется на хосте или в CI.
- Выделить планировщику отдельный режим зеркала и отдельную конфигурацию прав. Ему нужны неурезанная история и право писать задачи, права исполнителя с ними не смешиваются.
- На пилоте проверить, что пустая очередь и отказ `push` не превращают цикл в бесконечный повтор, что задача не выдаётся дважды, что запись в основную ветку остаётся запрещённой и что чужой репозиторий недоступен обеим ролям.

## Интеграция с провайдером прокси

- Оставить ручную настройку. Опционально добавить подключение API провайдера и выбор прокси для конкретной VM из списка в приложении.
- Хранить ключ API вне гостя. Проверять новый прокси перед сменой. Если проверка не прошла, сохранять действующую конфигурацию.
- Проверить две VM с разными upstream и подтвердить фактический внешний IP каждой. При недоступном прокси и обращении к запрещённому адресу проверять отказ без прямого выхода в интернет.

## Пилот и критерии 1.0.0

- Заказчик устанавливает CLI по инструкции на Linux-хост и выполняет весь рабочий сценарий в одном терминале. Во время пилота предоставляем полный функционал для оценки.
- Проверены создание двух гостей, работа с Claude Code и Codex, переключение между VM и сессиями, переподключение, перезапуск с сохранением проектов и авторизации.
- Пройдены проверки из раздела [Проверка изоляции KVM и прокси](#проверка-изоляции-kvm-и-прокси) и проверены права Git-шлюза. Интеграция с API прокси опциональна. Ручной настройки достаточно для релиза.
- Опубликованы бинарник, контрольная сумма и руководство по установке, обновлению и сохранению данных.

## После 1.0.0. Монетизация

Решение о платных возможностях и цене принимаем после пилота. Проверяем, какие функции заказчик использует регулярно и за какие готов платить.

- Основная гипотеза - бесплатная локальная версия с одной VM, одним выбранным агентом, сохранением сессий и ручной настройкой прокси. Подписка даёт управление несколькими VM и живыми сессиями, Git-шлюз и интеграцию с API прокси.
- Альтернатива - полный доступ на пробный период с подпиской для продолжения работы.
- Подписка покрывает продукт для управления окружениями. Claude Code и Codex работают с аккаунтом пользователя и его тарифом. Если локальное ядро остаётся открытым, платные возможности можно поставлять как отдельное дополнение или сервис.
