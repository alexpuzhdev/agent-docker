# agent-docker

Единственный репозиторий: `agent-docker`. Базовая ветка для работы над гостевыми VM: `v2-kve`.

- Настройка первого гостя: `make` или `make vm-setup`.
- Сценарии Docker Compose для гостевой VM хранятся в `v2/compose.yaml`.
- Проверка shell-сценариев: `bash -n v2/manage.sh v2/start-vm.sh v2/guest.sh v2/prepare-base.sh v2/prepare-guest.sh v2/serial-profile.sh v2/guest-dev-tools.sh cli/install.sh v2/install-sessions-guest.sh v2/atrice-tmux-profile.sh`.
- Проверка JS: `node --check` для каждого изменённого файла `.cjs`.
- Проверка Git-шлюза: `node --test v2/tests/test_git_gateway.cjs` и `python3 -m unittest v2/tests/test_git_mirror.py`.
- Проверка журнала SNI: `node --test v2/tests/test_sni_log.cjs`.
- Проверка настройки Git через Make: `bash v2/tests/test_vm_setup_git.sh`.
- Проверка статуса Git-шлюза: `bash v2/tests/test_vm_git_status.sh`.
- Проверка журналов, профиля и удаления гостя: `bash v2/tests/test_vm_manage_targets.sh`.
- Сквозная проверка GitLab по HTTPS на подставном сервере: `bash v2/tests/test_gitlab_https.sh`. Нужны `python3`, `git`, `openssl` и `git-http-backend`; сеть не требуется, стенд работает на loopback. Первым аргументом можно передать путь к проверяемому `git-mirror.py` — это нужно для мутационных прогонов на копии.
- Проверка терминального приложения: `gofmt -l cli`, `go vet ./cli` и `go test ./cli`.
- Проверка подготовки гостя и поиска устройства cloud-init: `bash v2/tests/test_prepare_guest.sh`.
- Проверка гостевой консоли: `python3 -m unittest discover -s v2/tests -v`.
- Этап сквозного теста: `make vm-setup VM=vm-01`, проверка результата установки, затем `make vm-stop VM=vm-01` и повторный запуск с тем же диском.
- Шлюз принимает HTTP и HTTPS только во внутренней сети Compose. Порты 80 и 443 на хосте не публикуются.
- Исходники терминального приложения `atrice` лежат в `cli`. Оно не повторяет логику `v2/manage.sh`, а вызывает его цели и не работает с токенами.
- Инструменты разработки в госте: `bash v2/guest-dev-tools.sh --check` сверяет набор и версии,
  минимум для Go берётся из директивы `go` в `go.mod`. `--install` доставляет недостающее из
  разрешённых источников (`/etc/apt/agent-docker.list`: `deb.debian.org` и `downloads.claude.ai`
  через upstream-прокси) и требует root, поэтому запускается на отдельном стенде, а не в живом
  госте. При полном наборе apt не вызывается, так что повторный запуск безопасен.
- Проверки Go в госте запускайте с `GOTOOLCHAIN=local`: прямого выхода в сеть нет, и расхождение
  с директивой `go` должно давать отказ, а не загрузку тулчейна.
- Для `go test -race` нужны gcc и `libc6-dev`: без стандартных заголовков C сборка детектора
  гонок падает в `runtime/cgo` на `stdlib.h`, хотя `gcc --version` отвечает исправно.
  `libc6-dev` стоит у gcc только в `Recommends`, а они отключены `--no-install-recommends`,
  поэтому `guest-dev-tools.sh` проверяет заголовки отдельно от наличия компилятора.
- Проверка доставки гостевых инструментов: `bash v2/tests/test_guest_dev_tools.sh`. Настоящие apt,
  сеть и root не нужны — набор инструментов подставной.
- Docker, `docker compose`, `qemu-system-x86_64`, `qemu-img` и `genisoimage` нужны только на хосте
  Docker: остальные проверки из этого списка обходятся подставными командами в `PATH`.
- Сборка и установка приложения: `make atrice` собирает бинарник в корне проекта,
  `make atrice-install` ставит его в `~/.local/bin` без root. Привязка каталога проекта
  записывается только по `bash cli/install.sh --bind` и не перезаписывается без него.
  Приложение не смотрит на argv[0], поэтому ранее собранный `agd` продолжает работать.
- Проверка установки приложения: `bash v2/tests/test_atrice_install.sh`. Настоящий Go,
  сеть и root не нужны — сборку изображает подставной `go`.
- Канал живых сессий: отдельный virtio-serial, `/guest/control.sock` со стороны контейнера и
  `/dev/virtio-ports/atrice.control` со стороны гостя. Сети и портов не добавляет. Запрос и ответ —
  по одной строке JSON; разрешены только операции `hello` и `sessions`, произвольных команд в
  канале нет. Версия контракта — `api: 1`; хост проверяет структуру ответа, ограничивает его
  размер (`AGENT_DOCKER_CONTROL_LIMIT`) и срок (`AGENT_DOCKER_CONTROL_DEADLINE`).
- Коды возврата `v2/sessions.py` различают причины: 0 — список получен, 2 — ошибка вызова,
  3 — канала нет (сокета не существует или подключиться не удалось), 4 — ответ превысил предел
  размера, 5 — ответ не прошёл проверку структуры, 6 — ответа нет совсем (служба не запущена или
  не смогла открыть порт), 7 — ответ начался, но не поместился в срок, 8 — служба работает, но не
  видит сервер tmux (чужой UID), 9 — в образе нет tmux. Несовместимый образ список должен
  показывать, а не падать.
- Срок на канале единый: он отсчитывается монотонными часами от подключения до конца ответа.
  Тайм-аут на каждом чтении отдельно позволял задержкам складываться — ответ из фрагментов по
  80 мс проходил при сроке 150 мс. Регрессия на медленные фрагменты закреплена тестом.
- Порт virtio непозиционируемый, и `open(port, 'r+')` для него не годится: текстовый режим r+
  строит `BufferedRandom`, которому нужен `seek`, и даёт `io.UnsupportedOperation`. Гостевая
  служба открывает порт одним дескриптором через `os.open` и читает `os.read` без буферизации;
  модель проверяется на паре PTY.
- Права на порт даёт узкое правило udev `/etc/udev/rules.d/60-atrice-control.rules`: совпадение
  по `ATTR{name}=="atrice.control"`, `GROUP="agent"`, `MODE="0660"`. Остальные порты virtio прав
  не меняют. Служба `atrice-sessions.service` работает под `User=agent` — root ей не нужен, иначе
  она не увидит сервер tmux агентов. `PrivateTmp` в юните запрещён: прежний сокет tmux лежит в
  `/tmp` и остаётся вторым проверяемым путём. `PrivateNetwork=yes` закрывает сеть структурно.
- Новым гостям канал ставит cloud-init при первом запуске: правило, юнит и служба перечислены в
  `write_files`, а `runcmd` перечитывает udev и поднимает службу.
- `instance-id` менять нельзя. cloud-init применяет `write_files` и `runcmd` один раз на
  `instance-id`, но его смена делает гостя «новым» и для остальных модулей: на копии старого диска
  так сгенерировался новый ключ хоста ED25519 и изменился его отпечаток. Поэтому автоматического
  повторного провижинирования нет, и тест следит, чтобы ревизия не вернулась.
- Существующим гостям канал ставит `v2/install-sessions-guest.sh` — узкий идемпотентный шаг. Он
  записывает ровно пять файлов (служба, юнит, правило udev, файл tmpfiles с каталогом сокета и
  `profile.d` с его путём) и только если содержимое отличается;
  ключи хоста, учётные данные, профиль VM, `/etc/hosts` и домашние каталоги не читаются и не
  перезаписываются. Это **операторский шаг**, его запускает человек:
  предпочтительно `--install --root /mnt/guest` на остановленном госте, корень которого
  смонтирован на хосте (root внутри гостя не нужен); либо `--install` внутри работающего гостя
  от root. `--check` работает без root и ничего не пишет, включая каталог включения.
  `--with-tmux` ставит tmux только при его отсутствии и только из `agent-docker.list`.
  Агенту новых прав при этом не выдаётся, сеть не используется.
- Офлайн-режим сам включает юнит: создаётся ссылка
  `<root>/etc/systemd/system/multi-user.target.wants/atrice-sessions.service` →
  `/etc/systemd/system/atrice-sessions.service`, то есть ровно то, что делает
  `systemctl enable`, поэтому `systemctl --root=DIR is-enabled atrice-sessions.service`
  отвечает `enabled`. Служба на хосте при этом не запускается, systemd на хосте не нужен,
  повторный запуск при верной ссылке ничего не меняет.
- Корень гостевого диска недоверенный, поэтому все целевые пути проверяются до любых изменений:
  символическая ссылка в родительском каталоге, в самом целевом файле или в пути включения —
  отказ с кодом 3 и названным путём; цель, существующая не обычным файлом, — тоже отказ.
  Единственная разрешённая ссылка — сама ссылка включения, и её значение сверяется с путём юнита
  внутри гостя. Для офлайн-режима `--root` обязателен, непуст и не равен `/`.
- Правило udev и юнит лежат отдельными файлами `v2/atrice-control.rules` и
  `v2/atrice-sessions.service`: их ставят и `seed.py`, и установщик, расходиться им нельзя.
  В `COPY` Dockerfile добавлены `*.service` и `*.rules`, иначе в контейнер они не попадут.
- Проверка узкой установки: `bash v2/tests/test_install_sessions_guest.sh`. Установка идёт в
  подставной корень через `--root`, поэтому root, настоящий гость, apt и сеть не нужны.
- Поля в `list-sessions -F` разделяются печатной последовательностью `|@|`. Управляющий байт тут
  не годится: tmux 3.5a экранирует непечатные символы в выводе, и ASCII US выходил буквальными
  `\037` — разбор не находил разделителя и отдавал пустой список вместо живых сессий. Свободное
  поле (`pane_current_command`) идёт последним и отделяется с ограничением числа частей.
- Сокет tmux один и общий: `/run/atrice/sessions/atrice`. Каталог сокета создаётся заранее файлом
  `/usr/lib/tmpfiles.d/atrice-sessions.conf` (`d /run/atrice/sessions 0770 agent agent`), путь
  экспортируется агентам в `/etc/profile.d/atrice-tmux.sh` как `ATRICE_TMUX_SOCKET`, и сессии
  запускаются как `tmux -S "$ATRICE_TMUX_SOCKET"`. Ни агент, ни служба каталога не создают.
- Ответ службы не зависит от того, запускался ли tmux в госте хоть раз. Метка `-L` заставляет tmux
  создать каталог сокета (`<TMUX_TMPDIR>/tmux-<uid>`), а при `ProtectSystem=strict` вся иерархия
  только для чтения и `mkdir` отвечает EROFS: на чистой Debian KVM первый запрос до любого запуска
  tmux давал `tmux-failed`, а после обычного вызова tmux тот же запрос отвечал `[]` ещё до
  появления сервера. Теперь служба ищет сокет сама — `stat` по точному пути, без вызова tmux, — и
  вызывает `tmux -S <путь>` только для найденного сокета. Ограничения службы при этом не
  ослаблены: подключение к существующему сокету на дереве только для чтения разрешено, EROFS
  проверяется лишь для обычных файлов, каталогов и ссылок.
- Состояния сокета четыре и они различны: `present` — опрашиваем, `absent` (ни по выделенному
  пути, ни по прежнему `/tmp/tmux-<uid>/atrice`) — пустой список, `denied` (`PermissionError` на
  `stat`) — `no-permission`, не сокет по пути или иной `OSError` — `tmux-failed`. Отказ доступа
  пустым списком не маскируется ни в одном из них. `hello` показывает это состояние полем
  `socket` — добавка в рамках `api: 1`.
- Отсутствие сервера tmux — успех с пустым списком, а не отказ. Текст stderr tmux остаётся второй
  линией: `no server running on <путь>` и `error connecting to <путь> (No such file or directory)`
  оба означают «сессий нет». Отказ доступа (`Permission denied`) разбирается раньше и остаётся `no-permission`, прочие
  отказы — `tmux-failed`; отсутствие tmux определяется отдельно по `tmux -V`. Четыре исхода
  различны, и ни один отказ не превращается в пустой список.
- tmux вызывается с `LC_ALL=C` и `LANG=C`: текст ошибки берётся из `strerror` и в другой локали
  переводится, а разбор по переведённой строке не срабатывал — отсутствие сервера выглядело
  неизвестным отказом.
- Пустой список и неразобранный формат — разные вещи. Если tmux напечатал строки, но ни одна не
  совпала с форматом, служба отвечает `format-unparsed` (код 5). Частично разобранный вывод даёт
  список разобранных записей и необязательное поле `skipped` с числом пропущенных строк: это
  добавка в рамках `api: 1`, читатель, который её не знает, просто её не заметит.
- Идентификаторы наших сессий: `^[A-Za-z0-9][A-Za-z0-9-]{0,63}$`, например `20261123T0915-9f3c`.
  Такое имя tmux принимает (нет точки и двоеточия), не содержит разделителя и не требует
  экранирования в выводе. Чужие сессии с пробелами и неожиданными символами всё равно
  показываются — разбор на них рассчитан.
- Канал только читает. Гостевая служба `v2/sessions-responder.py` выполняет лишь читающие команды
  tmux с фиксированными аргументами, без оболочки, и не содержит `send-keys`, `kill-session` и
  `attach`: опрос не должен быть заметен работающему агенту. В пользовательскую serial-консоль
  канал не пишет — это закреплено тестом.
- Список живых сессий: `make vm-sessions VM=vm-02` или `atrice sessions vm-02`. Цели сессий и
  диагностики перечислены в `Makefile` и уходят в `manage.sh` без своей логики: `vm-sessions`,
  `vm-sessions-check`, `vm-shell-check`, `vm-session-open`, `vm-session-claude`, `vm-session-new`,
  `vm-session-direct`, `vm-session-direct-check`. Документация обязана звать только существующие
  цели: `make` на отсутствующей цели отвечает отказом, и путь из GUIDE.md обрывался бы на нём.
- Диагностика подключения: `make vm-sessions-check VM=vm-02`. Одна строка JSON на stdout и код
  возврата 0 при любом состоянии — показать состояние должен список на хосте, а не отказ команды.
  Поля: `api`, `state`, `hint`, необязательные `detail` и `skipped`, `tmux`, `socket`, `sessions`,
  `console`. Состояния `state` различны и не подменяют друг друга: `old-image` — образ без канала,
  `no-service` — канал есть, служба не ответила, `no-tmux` — в образе нет tmux, `no-permission` —
  служба не видит сокет, `format-unparsed` — вывод tmux не разобран, `slow` — ответ не поместился
  в срок, `broken` — ответ не прошёл проверку, `empty` — живых сессий нет, `live` — список
  получен. `console` отвечает отдельно: `free`, `busy` или `unknown`.
- Занятость консоли определяется по тому же файлу блокировки, что берёт `console.py`
  (`/guest/console.lock`, `AGENT_DOCKER_CONSOLE_LOCK`): блокировка берётся неблокирующе и сразу
  отпускается, файл не создаётся. Ни сокет консоли, ни её журнал, ни tty при диагностике не
  открываются и не записываются — это закреплено тестом на pty и на подставном `serial.sock`.
- Обычная serial-консоль по `c` работает на любом образе и ни от канала, ни от tmux, ни от
  наличия агента не зависит: `consoleTrouble` в `cli/menu_view.go` смотрит только настройку и
  запуск гостя, и это закреплено тестом Go.
- Хостовый адаптер отчёта живёт в `cli/live.go`, и колонка «СЕССИИ» берёт данные только из него:
  память CLI о прошлых входах в неё не попадает, иначе запись о давнем входе выглядела бы живой
  сессией. Опрос идёт целью `vm-sessions-check` через `captureManage` — без наследования терминала,
  потому что список держит ввод в неформатированном режиме, — только для запущенного гостя и не
  чаще `liveTTL` (пять секунд); клавиша `r` забывает кэш. Отказ самого опроса — отдельное
  состояние `no-report`: про сессии в этом случае неизвестно ничего, и пустым списком оно не
  подменяется. Незнакомое `state` показывается как есть, `console: busy` — отдельной отметкой и
  без запрета клавиши `c`. Проверки: `TestLiveTextDistinguishesStates`,
  `TestApplyLiveReportsProbeFailure`, `TestListColumnTakesSessionsOnlyFromChannel` в `cli/`.
- Клавиши списка читаются рунами (`cli/keys.go`): русская буква в UTF-8 занимает два байта, и
  разбор по первому байту сводил всю раскладку к 0xD0 и 0xD1 — ни одно действие с неё не
  вызывалось. Раскладка сворачивается по расположению клавиш (ЙЦУКЕН → QWERTY), регистр снимается.
  Проверки: `TestDecodeKeyFoldsRussianLayout`, `TestRussianLayoutReachesEveryAction`.
- `Enter` в списке открывает экран живых сессий гостя (`sessionsScreen`, `renderSessions`), а не
  запускает агента вслепую: в занятой оболочке `console.py` отвечает отказом, и вход срывался
  именно так. С экрана `c` открывает консоль, `a` запускает агента, `r` обновляет, а `Ctrl+]`,
  `Esc` и `q` возвращают в список. Выбор цели для `atrice go` (`lastSession`) решает канал: живые
  сессии — консоль, пустой список — агент, а на старом образе и при отказе опроса решает память
  CLI. Клавиши экрана проверяются через `readMenuKey` без tty: `TestSessionsScreenKeysChooseTarget`,
  `TestResumeFollowsChannelSessions`, `TestResumeFallsBackToMemoryOnOldImage`.
- Блокировка консоли `/guest/console.lock` принадлежит процессу `console.py`, и закрытый хостовый
  терминал она переживать не должна. Два пути потери клиента различны: закрытое устройство pty
  видно изнутри (чтение отдаёт EOF или EIO, узел `/dev/pts/N` исчезает, `terminal_gone` проверяет
  это и по тишине в консоли), а ушедший клиент `docker exec` при открытом мастере изнутри не виден
  вовсе — об этом сообщает хост. Поэтому `open_console` в `manage.sh` выдаёт каждому входу токен
  (`AGENT_DOCKER_CONSOLE_TOKEN`) и по ловушке на `HUP`, `TERM` и выходе вызывает
  `console.py --release '' <токен>`: завершается ровно та консоль, которую этот вход и запустил.
  Условия освобождения строгие — блокировка занята, запись владельца есть, токен совпадает, процесс
  действительно `console.py`; иначе не делается ничего, и чужая работающая консоль не отключается.
  В serial-сокет ни один из путей не пишет, поэтому агент и сессии tmux переживают уход клиента.
  Владелец записан в самом файле блокировки (`pid`, `tty`, `token`), и отказ при занятой консоли
  называет процесс. Проверки: `python3 -m unittest v2.tests.test_console` — закрытие терминала,
  освобождение по токену, отказ освобождать чужую консоль, EOF изнутри гостя.
- Токен консоли в `open_console` берётся без конвейера: `tr -dc ... | head -c 32` под
  `set -euo pipefail` обрывает `tr` сигналом SIGPIPE, конвейер отдаёт 141, и `errexit` заканчивал
  цель до `docker exec` — консоль не открывалась вовсе. Теперь 16 байт читает сам `od -An -vtx1
  -N16`, лишние символы снимает подстановка параметра, а длина проверяется. Любой новый генератор
  обязан обходиться без конвейера с досрочно закрывающимся читателем.
- Цель `vm-session-open` отделена от `vm-console` и агентов: на этом пути нет ни `start_guest`, ни
  `wait_ready`, а остановленный гость получает отказ — подключение к существующей сессии не должно
  ни поднимать ВМ, ни запускать нового агента. Проверка:
  `bash v2/tests/test_vm_console_targets.sh` — настоящая точка входа `manage.sh` с подставным
  docker: токен длиной 32, запуск `docker exec`, освобождение тем же токеном, оба состояния ВМ и
  точный `RESUME`.
- К уже подключённой сессии возвращаются обычной консолью, а не вторым `attach`: её клиент `tmux`
  занимает оболочку гостя, и отправленные байты ушли бы этому клиенту как нажатия. Признак берётся
  из поля `attached` отчёта канала (`attached` в `cli/menu_view.go`), а `console.py` на занятой
  оболочке отказывает понятным текстом. После `Ctrl+]` или закрытия внешнего PTY сессия и агент в
  ней остаются живы: при отсоединении в гостя не отправляется ничего. Проверки:
  `TestAttachedSessionReturnsThroughConsole`, `test_session_attach_survives_detach_and_allows_reentry`.
- Подключение к живой сессии идёт целью `vm-session-open` и переменной `RESUME` — тем же каналом,
  которым передаётся `claude --resume`; новой переменной не вводится. `console.py` проверяет имя
  сессии по контракту канала (`^[A-Za-z0-9][A-Za-z0-9-]{0,63}$`), требует свободной оболочки, как и
  запуск агента, и отправляет `exec tmux -S "$ATRICE_TMUX_SOCKET" attach -t <имя>`. Канал сессий
  остаётся читающим: `attach` выполняет консоль, а не гостевая служба.
- Сокет сессий один для всех штатных путей — `$ATRICE_TMUX_SOCKET`
  (`/run/atrice/sessions/atrice`), и видно каналу только то, что на нём. Цель `claude` теперь
  запускает агента внутри управляемой сессии (`tmux new-session -s claude-<16 hex>`), а не прямо
  в serial-оболочке: прямой `exec claude` сессией tmux не был, канал его не видел вовсе
  (`state: empty` при работающем агенте), и после закрытия окна такой агент оставался на serial
  без пути возврата. В образе без tmux запуск остаётся прямым (`command -v tmux` в той же
  строке), иначе агент не запустился бы. `claude-auth` и `claude-logout` сессий не создают.
  Сессии, запущенные вне этого сокета (обычный `tmux` пользователя на `/tmp/tmux-<uid>/default`),
  каналу не видны намеренно: это сессии пользователя, а не Atrice, и считать их своими нельзя.
  Проверки: `test_agent_starts_in_a_managed_session`, `TestShellStateTellsSerialApart`.
- Состояние serial-оболочки приходит отдельной читающей целью `vm-shell-check`
  (`console.py --shell` → `{"api":1,"shell":"ready|busy|unknown"}`), а не каналом: канал по
  своему контракту журнала консоли не касается, и это закреплено его тестом
  (`test_reader_never_touches_user_console`). Режим читающий — блокировка не берётся,
  serial-сокет не открывается, tty не нужен, журнал не дописывается, — поэтому его можно
  спрашивать при живом агенте. Пустой список сессий и занятая оболочка — разные вещи: в списке
  это отметка «на serial работает приложение», на экране сессий — строка состояния, а запуск
  агента и новая сессия при `shell: busy` отказывают до отправки и называют безопасный путь:
  войти обычной консолью по `c` и завершить приложение штатно. Завершать чужие процессы и
  перезапускать ВМ для восстановления нельзя. Неоднозначность «процесс работает или метка
  устарела» снимается обновлённым профилем: он печатает отметку при каждом возврате к
  приглашению, поэтому её отсутствие означает занятую оболочку, а не устаревшую отметку.
- Размер окна, не переданный занятой оболочке, не теряется: он запоминается и уходит сам, как
  только оболочка вернёт приглашение (`pending_size` и `apply_size` в `v2/console.py`, досылка на
  тихом такте релея). В активную сессию `stty` не отправляется никогда — команда ушла бы клиенту
  `tmux` как нажатия клавиш. Проверка: `test_pending_resize_waits_for_a_free_shell`.
- Хвост журнала при входе начинается с целой строки (`safe_tail`): окно резалось по размеру и
  попадало в середину управляющей последовательности, её остаток терминал хоста понимал как
  мусор, и экран при переподключении выглядел повреждённым. Проверка:
  `test_tail_starts_at_a_whole_line`.
- Захват мыши приложением и залипание хоста различаются. По умолчанию (`MOUSE=app`) включения
  отслеживания проходят как есть: мышью распоряжается приложение, и обычное выделение в это время
  недоступно — это его право. `MOUSE=off` оставляет мышь терминалу: включения снимаются из
  потока гость→хост (в том числе разорванные между чтениями — остаток кадра переносится), а уже
  включённый режим сбрасывается сразу на входе; приложение щелчков не получает. В сторону гостя
  фильтра нет вовсе. Сброс режимов идёт на всех выходах консоли, а ловушка `open_console`
  сбрасывает их ещё и на терминале хоста — на случай, когда консоль в контейнере прервали вместе
  с `docker exec`. Проверки: `test_mouse_off_keeps_selection_for_the_host`,
  `test_console_cleans_private_modes_and_restores_terminal`.
- Прямой вход в управляемую сессию — второй, независимый от serial путь: отдельный порт
  virtio-serial `atrice.session` (`/guest/session.sock` со стороны контейнера, своя шина
  `atrice-ses` с явным адресом 0x1c — нумерация дисков не сдвигается), гостевая служба
  `v2/session-responder.py` со своим pty и своим клиентом tmux, хостовая половина
  `v2/session.py`. Serial-консоли этот путь не касается вовсе: её блокировка не берётся, в
  `/guest/serial.sock` не уходит ни байта, — поэтому создать и открыть сессию можно и при
  занятой оболочке. Канал списка (`atrice.control`) не затронут и остаётся читающим.
- Интерфейс узкий и типизированный: кадры (тип, длина, содержимое), операции только `ping` и
  `open`, из запроса берутся лишь имя по контракту канала и размеры окна, argv клиента
  фиксирован в службе (`tmux -S <сокет> new-session -A -s <имя> -- claude`), оболочки нет.
  `exec`, `send-keys` и чужая версия api отклоняются. `new-session -A` делает повторный запрос
  идемпотентным: с тем же именем он подключается, а не создаёт второй сессии.
- Включение — явный шаг оператора и только на стенде: порт появляется при следующем запуске ВМ
  (`v2/guest.sh`), а служба ставится тем же узким установщиком с явным флагом:
  `bash v2/install-sessions-guest.sh --install [--root DIR] --with-direct` добавляет к пяти файлам
  канала списка три файла прямого входа и включает его юнит. Без флага не ставится ничего нового.
  Проверка: `v2/tests/test_install_sessions_guest.sh` — установка без флага не создаёт файлов
  прямого входа, с флагом создаёт ровно восемь файлов и обе ссылки включения, повторный запуск не
  пишет ничего. Пока службы нет, хост видит `silent`, пока нет порта — `absent`, и
  в обоих случаях работает по-прежнему через консоль. Состояние приходит читающей целью
  `vm-session-direct-check`; в TUI при `direct: ready` `a` идёт целью `vm-session-new`
  (имя `claude-<16 hex>` выдаёт `manage.sh`), а `Enter` — целью `vm-session-direct` с точным
  именем подсвеченной сессии. Ни `compose up`, ни `console.py` на этих путях нет.
- Уход хоста на порту virtio изнутри гостя не виден, поэтому путь подтверждается keepalive:
  пропажа означает уход клиента, служба посылает клиенту tmux SIGHUP, он отсоединяется, а сессия
  и агент в ней остаются живы. Ctrl+] делает то же явным кадром. Размер окна доходит до клиента
  живой сессии: pty здесь наш, и `resize` меняет его через TIOCSWINSZ — ограничение serial на
  этом пути снято.
- Уход клиента на прямом пути различается двумя путями, как и у консоли. Исчезнувшее устройство
  pty видно изнутри (`terminal_gone` в `v2/session.py`, проверка на тихом такте релея), а ушедший
  клиент `docker exec` при открытом мастере изнутри контейнера не виден вовсе: реле продолжало
  работать и подтверждать путь keepalive, сессия оставалась `attached`, а `vm-session-direct-check`
  отвечал `silent`, пока процесс не завершали руками. Поэтому про такой уход сообщает хост:
  `manage.sh` выдаёт каждому входу токен (`AGENT_DOCKER_SESSION_TOKEN`, тем же генератором без
  конвейера) и по ловушке на `HUP`, `TERM` и выходе вызывает `session.py --release <токен>`.
  Освобождается ровно реле этого входа: совпадение по токену в окружении процесса и по его
  командной строке (`session.py` в операции `open`); иначе не делается ничего, и чужое живое
  подключение не трогается. Само реле на `HUP`/`TERM` уходит не молча: оно посылает службе кадр
  `detach`, поэтому клиент tmux отсоединяется сразу, не дожидаясь срока keepalive. В serial при
  этом не уходит ни байта, и канал списка остаётся читающим. Проверки:
  `test_surviving_relay_is_released_by_token` (блокер воспроизводится и снимается без ручного
  kill), `test_signal_detaches_client_at_once`, `v2/tests/test_vm_console_targets.sh` — токен
  длиной 32 и освобождение тем же токеном.
- Признак живого хоста на прямом пути — только кадры его собственной сессии: данные, keepalive,
  resize и detach. Кадр `open` или `ping` означает уже другого клиента: служба отпускает прежнюю
  сессию (клиент tmux получает SIGHUP, сессия и агент живы) и возвращает запрос в буфер, чтобы
  ответить на него обычным путём. Иначе запросы нового клиента обновляли счётчик keepalive,
  мёртвая сессия жила вечно, и повторный вход после закрытия окна становился невозможен совсем.
  Запись в порт тоже ограничена сроком: отключённый клиент не должен оставлять службу висеть
  внутри сессии. Проверка: `test_lost_host_detaches_client_and_keeps_session` — после гибели
  хостовой половины путь снова отвечает `ready`, сессия и агент живы.
- Кадры отправляет только цикл релея. Обработчик SIGWINCH в хостовой половине лишь запоминает
  размер и будит цикл самопроводом: запись из обработчика шла вперемешку с кадром цикла, поток
  на гостевой стороне терял синхронизацию, и вход зависал. Служба на такой случай страхуется
  сама: несобранный кадр дольше срока keepalive и заклинившая запись в pty означают уход
  клиента, а не остановку службы. Метка запроса (`id`) возвращается во всех ответах, поэтому
  кадр прошлого входа не принимается за ответ следующему. Проверки:
  `python3 -m unittest v2.tests.test_session_direct` — сквозной стенд с настоящими обеими
  половинами, мостом вместо порта и подставным tmux.
- Создать сессию при занятом serial текущим протоколом нельзя, и обходить это записью в
  неизвестный процесс запрещено. Путей записи в гостя всего два: serial-консоль (занята) и порт
  `atrice.control`, который по контракту только читает (`-monitor none`, qemu-guest-agent не
  установлен — других каналов нет). Поэтому `a` при `console: busy` или `shell: busy` отказывает
  до отправки и называет безопасный путь. Минимальный интерфейс для снятия ограничения описан в
  GUIDE.md разделом про параллельные сессии: одна типизированная операция `session-new` в
  гостевой службе, включаемая явным флагом установки, с именем по контракту канала и фиксированной
  командой `tmux new-session -d`. До согласования контракт не меняется.
- Команда `atrice sessions <VM>` обязана быть и в справке (`cli/help.go`), и в разборе
  (`cli/commands.go` → цель `vm-sessions`): в чистой сборке разбор её не знал, и обещанная
  справкой команда отвечала «неизвестная команда sessions», хотя установленный из грязного
  дерева бинарник отдавал отчёт. Проверка: `TestSessionsCommandKeepsItsContract` — справка,
  разбор и маршрут до `manage.sh` в одном тесте.
- Релей консоли ничего не фильтрует в живом потоке: приватными режимами терминала (мышь
  1000/1002/1003/1006, альтернативный экран 1049, скобочная вставка) распоряжается само
  приложение. А переигранный хвост журнала фильтруется (`private_mode` в `v2/console.py`):
  сырой хвост включал режимы прежнего приложения в терминале хоста — экран выглядел
  повреждённым, выделение требовало Shift, а при 1003 каждое движение мыши гнало байты в
  serial. На выходе консоль пишет сброс этих режимов в свой терминал и ничего в гостя.
  Размеры окна serial не передаёт, поэтому `SIGWINCH` отправляет `stty rows/cols` только
  свободной оболочке; при работающем приложении не отправляется ничего. Сам релей не медленный:
  на стенде 256 КиБ проходят за 0,05 с, задержка первого байта — единицы миллисекунд. Проверки:
  `test_console_cleans_private_modes_and_restores_terminal`, `test_resize_reaches_only_a_free_shell`.
- Новая сессия рядом с живой — цель `vm-session-claude` и операция консоли с тем же именем:
  имя `claude-<16 hex>` выдаёт `manage.sh` (без конвейера, как и токен) и называет его
  строкой «Новая сессия: …», а консоль отправляет `exec tmux -S "$ATRICE_TMUX_SOCKET"
  new-session -s <имя> -- claude`. `--resume` здесь не добавляется: `RESUME` в этой операции
  означает имя самой сессии. Прежние сессии цель не трогает — ни `attach`, ни `kill-session`,
  ни `send-keys`, — поэтому их процессы продолжают работать. Гостя цель не поднимает: у
  остановленной ВМ живых сессий нет, и для неё остаётся обычная цель `claude`.
- Создание новой сессии защищено так же, как подключение: нужна свободная оболочка по штатной
  метке возврата к приглашению. При занятой консоли отказ приходит до отправки, сессия не
  создаётся, и записи о входе не появляется (`noteSession` вызывается только после удачного
  запуска цели), поэтому повторное нажатие не плодит ложных записей в живом списке. Канал
  сессий остаётся читающим: создание идёт консолью, а не каналом, и его контракт не
  расширяется. Проверки: `TestNewSessionTargetRunsWithoutResume`,
  `TestNewSessionRefusalLeavesNoRecord`, `test_session_claude_starts_a_new_session_beside_the_old`,
  `test_session_claude_checks_name_and_busy_shell`, `v2/tests/test_vm_console_targets.sh`
  (уникальное имя, оба состояния ВМ, отсутствие `compose up` и запуска прежнего агента).
- Свободная оболочка определяется единственным признаком — отметкой возврата к приглашению
  `\x1b]9999;agent-docker-shell-ready\x07` после отсечки последней отправки
  (`console.pending`). Печатает её хук `PROMPT_COMMAND` из `v2/serial-profile.sh`, и печатает
  при каждом настоящем возврате Bash к приглашению: прежняя версия хука снимала себя после
  первого приглашения входа, из-за чего после обычной команды признака больше не было и
  `vm-session-open` отказывал ложно. Хук идёт последним, возвращает статус предыдущей команды
  (его видят и пользовательский `PROMPT_COMMAND`, и `PS1`), не дублируется при повторном входе
  в профиль и действует только в интерактивной оболочке `agent` на `/dev/ttyS0`.
- По видимому тексту журнала готовность определять нельзя: строку, похожую на приглашение,
  печатает и работающая на переднем плане программа (`progress # `, `amount: 5$ `), а
  отправленный в неё `tmux attach` ушёл бы ей как нажатия клавиш. Проверки:
  `test_prompt_lookalike_output_is_not_readiness`,
  `test_session_open_after_finished_command_sees_free_shell`, `v2/tests/test_serial_profile.py`
  (отметка на каждом приглашении, сохранённый `PROMPT_COMMAND` и статус, область действия,
  отсутствие дублей и видимого шума).
- Гость, созданный прежней версией, получает профиль не сам: cloud-init записывает
  `/etc/profile.d/agent-docker-serial.sh` один раз при создании. Обновление без пересоздания —
  скопировать в гостя новый `v2/serial-profile.sh` и войти в оболочку заново; до этого
  `vm-session-open` на таком госте работает только сразу после входа в Bash, а обычная консоль
  (`vm-console`) и запуск агента из свежей оболочки работают как раньше. Порядок — в GUIDE.md.
- `Enter` в списках — только подтверждение подсвеченного пункта: в списке гостей выбирает гостя и
  открывает его живые сессии, в списке сессий подключается к подсвеченной. Ни гостя, ни агента
  `Enter` сам не запускает и оболочку не открывает; при пустом списке не делает ничего. Обычная
  консоль и запуск агента — отдельные пункты `c` и `a`. Выбор сессии держится за её именем, а не за
  номером строки: список перечитывается из канала. Проверки: `TestSessionsScreenKeysChooseTarget`,
  `TestSessionsScreenEnterNeedsSelection`, `TestMenuTargetCarriesSessionInResume`.
- Клавиши разбираются в `cli/keys.go` рунами: стрелки принимаются и как CSI (`ESC [ A`), и как SS3
  (`ESC O A`) — режим приложения включают tmux и screen, — а `Enter` принимается и как CR, и как
  LF. Проверки: `TestDecodeKeySpecialKeys`, случаи CSI и SS3 в `TestSessionsScreenKeysChooseTarget`.
- Контракт для хостового полноэкранного Atrice (двухвкладочного) и его JSON-адаптера на Go:
  вкладка списка гостей не меняется, вкладка сессий берёт данные только из
  `vm-sessions-check` — одна строка JSON, `state` и `hint` показываются как есть, `sessions`
  рисуется списком. Нужные изменения backend на хосте: 1) декодировать новый отчёт и не считать
  любой ненулевой код «сессий нет»; 2) различать все девять состояний, а не сводить их к паре
  «есть/нет» — подсказки у них разные; 3) неизвестное значение `state` показывать как есть, не
  падая: поле расширяемо в рамках `api: 1`; 4) `console: busy` показывать отдельной отметкой и не
  запрещать по ней клавишу `c` — отказ придёт от `manage.sh` и останется на экране; 5) опрос
  вести не чаще, чем раз в несколько секунд, и только для запущенного гостя: состояние
  контейнеров хост знает сам. Гостевую копию приложения и адаптера здесь не трогаем.
- Проверка канала сессий: `python3 -m unittest v2.tests.test_sessions_channel`. Гость подставной,
  tmux, KVM и сеть не нужны.
- Гостевая служба сессий в образ пока не заводится: `v2/sessions-responder.py` лежит в репозитории,
  а её установка через cloud-init и юнит systemd — следующий шаг. До него любой существующий гость
  отвечает как несовместимый образ, и это ожидаемое поведение.
- Процедура для гостя, созданного до появления канала, описана в `GUIDE.md` разделом «Старый
  гость: установка tmux и канала сессий»: обновление образа на хосте, офлайн-установка пяти файлов
  на смонтированном корне остановленного гостя и однократная служба `atrice-tmux-install.service`,
  которая ставит tmux из `/etc/apt/agent-docker.list` и становится инертной по
  `ConditionPathExists=!/usr/bin/tmux`. Шаги выполняет уполномоченный оператор, а не агент;
  `instance-id`, ключи хоста, учётные данные и `profile.json` не затрагиваются, и это проверяется
  по отпечатку ключа и строке готовности до и после.
- Инструкция для пользователя находится в `GUIDE.md`.
